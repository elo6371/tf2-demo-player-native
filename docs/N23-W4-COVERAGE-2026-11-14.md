## 1 方法（为什么不是 grep 计数）

分三步，每步都有可复核的产物：

1. 从 `native/cmake/*.cmake` + `native/CMakeLists.txt` 解析 `add_executable(` 的**目标名**；
2. 解析 `target_compile_options(<target> ... /W4)` 得到施加集合；
3. **用生成的编译开关复核**——直接读 `native/build-nmake/CMakeFiles/<target>.dir/flags.make`，因为 CMake 源里的意图和实际传给 cl 的开关不是一回事。

第 1 步有个坑：`grep -c "add_executable("` 得到 58，其中 4 处是注释里的词（`tf2-libraries.cmake:5`、`tf2-version.cmake:85/86/89`）。按目标名去重后是 **54**。旧台账 D29 的"58 个 add_executable"就是被注释抬高的。

## 3 实测复核（两类各取一个）

```text
world_geometry_probe:  CXX_FLAGS = /DWIN32 /D_WINDOWS /EHsc /O2 /Ob2 /DNDEBUG -std:c++17 -MT /Brepro
hud_probe          :  CXX_FLAGS = ... /MT /Brepro /W4 /permissive- /EHsc /utf-8
```

`world_geometry_probe` 里没有任何 `/W`，所以它编译在 cl 的默认级别；`hud_probe` 是 `/W4`。这就是"6 个 vs 48 个"的实物依据，不是 CMake 源里的字面推断。

## 4 边界（这条盘点不证明什么）

- **没有量化 48 个目标在 `/W4` 下会报多少警告。** 要拿到这个数必须先加 `/W4` 再重建——那是改变，不是测量，属下一批。
- 6 个 `/W4` 目标**当前仍有警告**：最近一次完整构建里 `native_renderer_viewmodel.cpp(868)` 报 C4456、`xutility(4813)` 报 C4244（来自 `/W4` 目标）。也就是说 `/W4` 不等于"零警告"。
- 没有评估把 48 个抬到 `/W4` 会不会直接编译失败（MSVC 有些 C4xxx 在 `/W4` 下变成错误，取决于 `/WX` 未启用，本树未启 `/WX`）。

## 5 对后续警告治理的直接建议

1. **按 cmake 文件成批**，每批一个集成窗口；先做最大的三组（audio / core / world，各 6 个），因为它们共用 `tf2_core`，头文件改了影响面最大。
2. 每批只改 `target_compile_options`，**不动源码**；先看红，再决定是修源码还是给该目标单独降级——一次提交只做一件事。
3. `/WX` 不要一步上：先 `/W4` 跑几批，等 48 个目标都进 `/W4` 后再讨论是否升 `/WX`。
4. 门禁侧先加一条"新目标必须带 `/W4`"的检查（可以 grep `add_executable` 与 `target_compile_options` 的配对），防止覆盖率再退回 11%。
