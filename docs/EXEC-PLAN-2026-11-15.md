## 教训七：源码里跨行的 C 字符串不是输出行（lead，2026-11-14 20:43，直接导致 D56 登记错误）

缺陷增补里原有一条 D56「`playback-error-paths-check.sh` 取 `camera: summary` 的 `modeApplies=`，而 producer 根本没这个字段」。复核 gatefix 的实读结果时推翻：

- `native/src/main.cpp:13033-13035` 三行是一个 `traceFmt`：`"camera: summary mode=%s modeChanges=%u spacePresses=%u spaceSingles=%u"` / `" spaceDoubles=%u doubleWindowMs=%u pauseToggles=%u follows=%u holdsNoTarget=%u"` / `" freezeFrames=%u modeApplies=%u"`。**`modeApplies` 就在第三行末尾**，输出是一行。
- `native/src/main.cpp:12982-12983` 同理，`events_seen=%zu` 在第二行。
- 当初判「没有这个字段」，是因为 grep 在**源码**里只匹配到 `camera: summary` 所在的第一个物理行。**源码的换行是排版，输出的换行是语义**；两者混淆与 D51（注释当证据）、D53（环境当常量）同族，都会把「我没看见」写成「它不存在」。
- 同理：`native/src/install_lifecycle.cpp:794` 那种「第 2 行的形状被门禁钉死」的注释，讲的是**输出**行，不能拿源码行号去对应。

**做法**：任何「producer 不打印某字段」的结论，必须在**已有 trace 文件**里 grep 该字段名，或在源码里 grep 字段名本身（而不是 grep marker 行）。D56 已按此撤回并改写为 D53 的 CR 家族。

xargs -a /tmp/eol.txt git checkout --                     # 恢复它们，真实改动一律不碰
for f in $(git diff --name-only); do wt=$(tr -cd '\r' < "$f" | wc -c); hd=$(git show HEAD:"$f" | tr -cd '\r' | wc -c); [ "$wt" = "$hd" ] || echo "CRDIFF $f $wt/$hd"; done
