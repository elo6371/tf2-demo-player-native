# N26：同一台机器上的构建实测

2026-11-18 · 工程线（N26 的「待实测」）

## 0. 为什么现在测

卡片原本只有一条历史数字（编译动作 634→137、clean 648 s→221 s），来自另一台机器、另一份口径，**不是当前树、当前机器上的读数**。这一轮把四个场景在同一台机器、同一把构建锁、同一个工具链下重测了一遍，目的不是「看起来变快了」，而是拿到能拿来判断瓶颈的基线：到底是 configure、链接、还是头依赖在决定一次全量构建。

## 1. 口径

| 项 | 值 |
| --- | --- |
| 机器/环境 | 当前这台开发机，Windows，MSYS bash，与门禁同一把 `tools/lockrun.sh n26` 锁 |
| 工具链 | MSVC 14.44.35207（日志里的 cl 路径），CMake + NMake Makefiles，Release |
| 构建目录 | `native/build-n26`（第一次为全新空目录），与门禁使用的 `native/build-nmake` 分开 |
| 目标 | `bash build-target.sh tf2_demo_native`（含 `tf2_core` 静态库 + demo 可执行文件） |
| 规模 | 86 个编译单元（`*.obj`）、1 个静态库、1 个 exe |
| 计时 | `date +%s%3N` 包住 `build-target.sh` 整次调用；每次单独一次，不取平均 |
| 动作数 | 按 `*.obj` 的 mtime 分相位统计（NMake Makefiles 不逐条打印编译命令行，所以数的是「真的重新编译了哪些目标文件」，不是「日志里有几行」） |

## 2. 读数

| 场景 | 墙钟 | 重新编译的 TU | exe |
| --- | --- | --- | --- |
| 全新目录 configure | **1.88 s** | — | — |
| 全量（clean） | **121.25 s** | 86 / 86 | `96c47828…f508`，3,266,048 B |
| 全量后立刻再构建（no-op） | **3.06 s** | 0 | 同上，未变 |
| 改一个实现文件（`native/src/native_renderer_frame.cpp`） | **4.70 s** | 1 | 同上（逐字节相同） |
| 改一个公共头（`native/include/native_renderer.h`） | **118.88 s** | **81 / 86 = 94%** | 同上 |

clean 的 121.25 s 里 configure 只占 1.88 s，剩下约 119 s 是编译 + 链接。

## 3. 四个结论

### 3.1 头依赖是唯一的杠杆，别的都不是

动一个公共头会让 86 个 TU 里的 81 个重编，耗时 118.88 s，与全量 clean 的 121.25 s 几乎相同——也就是说**一次「小改」在头这一层等于一次全量重编**。configure（1.88 s）和 no-op（3.06 s）都不是瓶颈；真正决定构建时间的是「`native/include/native_renderer.h` 被几乎所有 TU 包含」这一件事。

这也给「要不要上缓存」定了调：先做的是减少头依赖（前向声明、拆小头、pimpl），而不是先给一个 94% 都会重编的工程加编译缓存——缓存只会把同一件事换个地方付钱。

> **更正（2026-11-18 晚）**：上面这段的归因错了。`native_renderer.h` 在本次真的被编译的 92 个 obj 里只被 **19** 个包含；118.88 s 来自 `build-target.sh` 的 stamp 守卫把任何头改动放大成 touch-all 全量重编，不是「几乎所有 TU 都包含它」。实测与改法见 `docs/N26-DEPENDENCY-ACCURACY-2026-11-18.md`。「头是关键杠杆」这个方向仍然成立（19 个 obj / 62 s 依然远大于改实现文件的 4.70 s），但「一次小改 = 一次全量重编」是守卫造成的，扇出本身没有那么大；3.2 里「NMake 缺头依赖的老问题没有在这条路径上暴露」也只在守卫兜底的意义上成立——依赖文件本身是有内容的、且被 nmake 消费，见同一份文件。

### 3.2 增量构建本身是健康的

no-op 3.06 s、单 TU 4.70 s，都落在「一次正常编辑循环感觉不到」的范围。NMake 缺头依赖的老问题没有在这条路径上暴露（`build-target.sh` 有 header-stamp 守卫）。

### 3.3 全新目录的构建结果和既有目录逐字节相同

`native/build-n26/tf2_demo_native.exe` 与门禁一直在用的 `native/build-nmake/tf2_demo_native.exe` 的 sha256 **完全相同**（`96c478283a068130ecbc0d7b3938bf9b485d0d3581d82e71ec5a1615eb97f508`，都是 3,266,048 B）。这一条顺带证明：至少在这个目标上，构建是可复现的，换目录不会换出一个「看起来一样但其实是另一支」的 exe。

### 3.4 warning 面：20 条（移交给 N23）

clean 日志里一共 20 条 `warning C…`：

| 代码 | 条数 |
| --- | --- |
| C4456（局部声明隐藏上一个） | 6 |
| C4244（窄化转换） | 6 |
| C4996（`swscanf`/`getenv` 不安全） | 4 |
| C4267（size_t→uint32_t） | 2 |
| C4457（遮蔽函数参数） | 1 |
| C4100（未引用参数） | 1 |

`tf2_core` 的编译选项里 `/W4 /permissive-` 是 PRIVATE（`native/cmake/tf2-libraries.cmake:113`）；这个数只说明「当前这棵树建一遍会打印 20 条」，**不是 N23 的覆盖率基线**——N23 要的是按目标、按警告类的完整清点，那件事还没做。

## 4. 这还没有证明什么

- **单次测量，没有方差**：每个场景只跑一次，机器上同时还有别的进程；几秒级的差异（例如 3.06 s 与 3.5 s）没有意义，只有分钟级差异（119 s 对 4.7 s）才是结论。
- **IO 没测**：卡片要的「IO」读数（磁盘读写字节、文件数）这一轮没有采，用的是墙钟。
- **只有一个目标**：`tf2_demo_native` 及其依赖。54 个探针目标的全量构建时间未知。
- **没有评估 PCH / ccache / unity build**：按卡片「先修实测瓶颈，再考虑缓存」，这些要等头依赖真的降下来再谈。
- **没测门禁全链**：`verify-fast.sh`、`verify-all.sh` 的耗时不在这一次里（那是另一条线，历史读数约 2.7 小时/全链，本轮未复测）。

## 5. 复现

```bash
cd /d/TF2_Native_Worktrees/t105-integrate
bash tools/lockrun.sh n26 -- bash .scratch/n26/measure.sh   # 脚本未入 git，四个场景一次跑完
```

脚本会先在 `native/build-n26` 建一个全新构建目录、跑 clean，然后依次 no-op、`touch` 一个实现文件、`touch` 一个公共头，每次记录墙钟、按 `*.obj` mtime 统计重编 TU 数、并打印 exe 的 sha256 前缀。

判断「是否真的重编」不要数日志行：NMake Makefiles 成功时**不打印**每条编译命令，要按目标文件的时间戳统计。
