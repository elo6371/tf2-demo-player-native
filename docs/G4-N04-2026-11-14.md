## 2 D46：探针把"打不开"报成成功（已修）

- **现象**：`demo_open_probe` 对 valid / truncated / badmagic / missing 四种输入**全部返回 0**，只在行内字段里写 `header=0 index=0`。任何按退出码判定的门禁都会把"文件根本不存在"读成成功。
- **修法**：在原有诊断不变的前提下，让状态与诊断一致：`0` 解析成功、`1` 打开但解析失败、`2` 打不开；多文件时取第一个非零。
- **验证**：valid `rc=0`、truncated `rc=1`、badmagic `rc=2`、missing `rc=2`；输出行与修前逐字相同。
- **边界**：这是探针契约修复，不改变产品行为；产品本身对两类畸形 demo 一直返回 rc=2（见 #1/#2）。

## 3 D47：启动期拒绝只写调试器（未修）

```bash
tf2_demo_native.exe --tf-root <tf> --audio-disabled --demo <ok.dem> --capture-tick abc
# rc=13, stdout+stderr = 0 bytes, trace = 3 行（open/window/args），没有任何原因
```

同类路径（`native/src/main.cpp` 约 1586/1634/1644/2986/2990/2994）：`--window-size`、`--settings-file`、`--ui-settings-file`、`--audio-device`、`--capture-tick`、`--animation-drive`。全部走 `OutputDebugStringW`，只有挂调试器才看得到。

- **影响**：用户双击启动失败没有任何提示；脚本只能拿到一个 13。
- **修法（建议）**：与 `demo open failed:` 一致，写 stderr 一行 `error: <flag> <reason>`，并在 `traceFmt` 里留一行；退出码保持 13 不变（调用方已在用的语义）。
- **为什么本轮不改**：属启动期参数路径，改动会触及所有 gate 的失败文本；应配一次全量门禁回归，不在"只读复核"里顺手改。

## 4 D48：注入的 D3D 失败被吸收，门禁仍报 PASS（未修，先记录）

`--renderer-resize-selftest --renderer-fault hud.createbuffer:0`：trace 里确实有

```
[renderer-resource] refuse surface=hud.createbuffer kind=create hresult=0x8007000E capacity=18 vertices=1800
```

但同一行末尾是 `RESULT=PASS checks=30 fail=0 ... refused=1`。

- 可能的设计意图是"资源失败要降级而不是崩"，这没错；
- 但门禁因此无法区分"优雅降级且画面正确"与"整块 HUD 没画"。
- 建议：故障注入运行时额外断言**受影响区域确实缺了什么**（像素或形状计数），否则这条注入用例只在证明"没崩"。
