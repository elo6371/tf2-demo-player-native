## 1 三个 DPI 问题，分别回答

任务卡的原话是"DPI 无入口"，但这句话把三件不同的事压成了一句。分开问：

### Q1 产品有没有 DPI 感知声明？—— **有**

- `native/src/main.cpp:1802-1805`：`:1802` 的注释是 "Keep the render surface in physical pixels on mixed-DPI desktop setups."；
  `:1803` `SetProcessDpiAwarenessContext(DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2)`，失败回落 `:1804` `SetProcessDPIAware()`。
- 全树**没有** `.manifest` 文件，`native/CMakeLists.txt` 里也没有 `dpiAware` 条目（grep 命中 0），
  所以结论是"用 API 声明感知"，不是"用 manifest 声明"。
- `native/src/main.cpp:1115-1139` 处理 `WM_DPICHANGED`：接受系统建议矩形**仅当没被 `--window-size` 钉住**，
  然后重排 UI 并打印 `window: dpi-changed dpi=%u pinned=%d client=%ldx%ld`。
- 采集侧也记了 DPI：`native/src/main.cpp:12842-12844` 打印 `capture: frame width=%d height=%d dpi=%u`
  ——格式化串在 `:12842`，`GetDpiForWindow(window)` 是它的实参（`:12844`）；`:12832-12840` 的注释解释了为什么
  画面尺寸必须在采集当帧读死（中途 resize 会让每个像素索引错位）。

### Q2 布局有没有按 DPI 缩放？—— **控件有，HUD 没有**

| 层 | 是否乘 DPI | 证据 |
|---|---|---|
| Win32 控件（按钮/静态文本/滑块） | **是** | `native/src/main_ui.cpp:45-47` 把 `GetDpiForWindow/96` 传进 `planUiLayout`；`native/src/native_ui.cpp:566-569` 的 `scaleDimension` 把每个基准数乘上去 |
| HUD 图元（小地图面板） | **否，故意的** | `native/include/hud_panel.h:131-134`：面板按**后备缓冲像素**钉死，理由写在注释里——"A DPI-scaled panel would move under the --window-size comparisons the pixel gates make" |

**后果**（算术，非猜测）：200% DPI 下控件占的面积翻四倍，面板仍是 160×160。
高 DPI 上"能不能看清"和"会不会撞"是两件事，后者见 §2。

### Q3 能不能不改显示设置就测真实 DPI 切换？—— **不能**

- 没有 `--dpi` / `--dpi-scale` 之类的命令行入口（grep `native/` 命中 0）；DPI 只能从 `GetDpiForWindow` 来。
- 真正切 DPI 要改显示设置——**本卡不许做**（如果做了，还要有人在场看着）。
- **能测的是纯函数** `planUiLayout(clientWidth, clientHeight, dpiScale)`，因为它不碰设备。本文件 §3 就是这么测的。

## 2 布局数学：现在成立，但小地图面板不在里面

### 2.1 遗漏：面板与状态栏在每个尺寸上都重叠

`planUiLayout` 只管 19 个控件，`planHudLayout` 只管 5 个 HUD 控件——**两者都不知道小地图面板存在**。
面板单独由 `hudLayoutPanels`（`native/include/hud_panel.h:57-122`，函数体起点 `:57`）算，调用点在 `native/src/main_hud.cpp:926-939`。

两者的坐标都在后备缓冲像素、原点都是客户区左上角，所以重叠就是真重叠不是坐标错。

| 窗口（外框） | 客户区 | 面板 | 占客户区 | 被面板压住的控件（重叠像素） |
|---|---|---|---:|---|
| 640x480 | 624x441 | 452,12,160,160 | 9.3% | Status 4368、Timeline 4680、Reverse 840、CameraMode 728 |
| 800x600 | 784x561 | 612,12,160,160 | 5.8% | Status 4368、Timeline 3120 |
| 1024x640 | 1008x601 | 836,12,160,160 | 4.2% | Status 4368 |
| 1280x720 | 1264x681 | 1092,12,160,160 | 3.0% | Status 4368 |
| 1366x768 | 1350x729 | 1178,12,160,160 | 2.6% | Status 4368 |
| 1920x1080 | 1904x1041 | 1732,12,160,160 | 1.3% | Status 4368 |
| 3840x2160 | 3824x2121 | 3652,12,160,160 | 0.3% | Status 4368 |

（客户区 = 外框 − 16 宽 − 39 高：1280x720→1264x681、800x600→784x561 两次实测同值，见 `docs/T3-MANUAL-FOLLOWUP-2026-10-14.md:20`。）

**为什么每个尺寸都命中**：状态栏矩形是"横跨边距之间的整个宽度、y=12、高 28"（`native/src/native_ui.cpp:653-657`），
面板是"右上角、y=12 起、160 高"。**它们在 y 方向起点相同**，所以面板顶部那 28 行必然落在状态栏矩形里。
实测重叠 156×28 = 4368 px = 面板面积的 17.1%。

DPI 1.5 时更差：状态栏高度变 42，重叠涨到 156×42 = 6216 px；800x600 下 `Reverse` 也被压住。

**这条要怎么定性**——两件事必须分开：

1. **布局数学上**：两个模块各算各的，谁也没读对方的矩形，**没有一处代码负责"控件不许和面板抢地方"**。这是确定的事实。
2. **视觉上是否真的挡住**：状态栏是 `STATIC` 控件（`native/src/main_ui.cpp:257`），
   它是否真的把面板顶部涂掉，取决于 Win32 控件重绘行为——而且**门禁永远看不见**：
   像素门禁读的是 D3D 后备缓冲（`native/src/native_renderer_capture.cpp:1` "Frame capture: back-buffer BMP writer"），
   而 Win32 子控件不在后备缓冲里。所以 A2 的 `inside=25600` 与 A4 的顶边边框检查都会照样通过。
   **这条属 NOT VERIFIED，需要一个可见窗口的截屏**（要有锁 + 有人看着），本卡没做。

   > 这条已作为 **D58** 登记在 `docs/DEFECT-REGISTER-ADDENDUM-D51-D56-2026-11-15.md:117-130`，其中的
   > 9.3% / 5.8% / 4368 / 17.1% / 156×42 与本文件同源。**本文件不重新评级**，只补两件事：
   > 判定依赖的行号已在 `6dd853e` 复核，以及 §4.2 记的"引用行号会随提交漂移"这一类错法。

顺带：`g_uiStatus` 是**始终可见**的——`updateNativeUiControls` 只对它 `SetWindowTextW`，从不调 `setUiControlVisible`，
而其它控件都按屏幕切换显隐（`native/src/main_ui.cpp:157-175`）。所以这条重叠不是某个屏幕特有的。

## 3 小地图面板的边界行为（可直接判断言）

| 断言 | 值 | 说明 |
|---|---|---|
| 面板尺寸恒定 | 160×160 | 与客户区、DPI 都无关（`hud_panel.h:136`，设计如此） |
| 面板 x | `client_w − 172` | 8 inset + 4 margin + 160；1264→1092、784→612 实测 |
| 面板 y | 恒为 12 | 8 + 4 |
| 放不下时 | **丢弃，不缩放** | `hud_panel.h:114` 的 `if (y < safeInset \|\| y + height > clientHeight - safeInset)` 走 drop，`:118` 的 `rect.placed` 随即为 false；产品报 `reason=panel-not-placed`（`main_hud.cpp:971`） |
| 最小可放置客户区高 | **180 px** | 低于此值 y+h 越过 `client_h − 8`，面板消失 |
| 最小可放置客户区宽 | **不存在**（见下） | |

**发现：丢弃规则只判 y 轴，不判 x 轴。** `hud_panel.h:114` 的条件是 `y < safeInset || y + height > clientHeight - safeInset`——
x 方向只做"夹进 `[safeInset, …]`"，于是客户区比 `2*safeInset = 16` 还窄时，面板被**放置**成 `x=8, w=0`：

| 客户区宽 | 面板 | placed | x 在客户区外？ |
|---:|---|---|---|
| 1 | 8,12,0,160 | true | **是** |
| 8 | 8,12,0,160 | true | 否（x==8 恰在边界） |
| 16 | 8,12,0,160 | true | 否 |
| 17 | 8,12,1,160 | true | 否 |
| 40 | 8,12,24,160 | true | 否 |

这是"放置成功但完全没用"的一格：宽度 0 的面板照样把 `state=ready` 报给门禁。
现实窗口达不到（`--window-size` 拒绝 <320x240 或 >8192：判据在 `native/src/main.cpp:1829-1830`，
报错串 `:1834`，返回码 13 在 `:1835`），
所以这是**逻辑漏洞而非可触发的产品缺陷**——但它是"丢弃规则"的第二条轴漏了，值得记。

## 4 本卡撞到的三个同类陷阱

三条的共性是一句话：**读的一方对输入或环境做了未经证实的假设，然后把假设的后果记成了结论。**
前两条已独立登记（D52 / D53），第三条是我自己在 N14 里犯的，写在这里是因为它比前两条更容易重犯——
前两条会报错或给出奇怪数值，第三条**什么都不会报，只会安静地给出一个不存在的结论**。

1. **UNSUPPORTED 不等于"产品没输出"**（N14 里踩的，本卡自犯）：D43 tier2 一直判 UNSUPPORTED，
   我一度当成"产品不打印 cp 行"。真相是**我喂进去的那份日志里没有 cp 行**——那份日志是修复后的回归日志，
   本来就不含 `minimap: cp name=` 行。换成七图各跑一次的采集后，26 条控制点线按名全中。
   规矩：判 UNSUPPORTED 之前，先证明输入里确实有这个数据。
2. **D53：判决取决于 PATH 上哪个 awk 在跑。** 同一门禁、同一份输入（`evidence/t62-matrix/pose-families/scout-crouch-seq10.txt`），
   worktree awk（dsh niubash `winuxcmd/usr/bin/awk.exe`）读出 CRLF 里的 `\r`，`printf 'a=1\r\n'` 上 `length($0)` 得 **4**；
   Git awk（`/c/Program Files/Git/usr/bin/awk.exe`）得 **3**。两个都是 GNU Awk 5.4.1、都是 4,647,424 B，
   差别只在读文件时做不做 CRLF 翻译。于是 `a[2] != "1"` 比的是 `"1\r"` 与 `"1"`，**永假**，
   `class-pose-family-check.sh:134` 的 40 帧全判非有限。教训：**"跑出来是绿色"不等于"门禁有效"，先问是哪个解释器给的绿。**
3. **D52：`> file` 在进程启动瞬间就截断。** `wall_ms=9116` 的探针在这 9 秒里留下一个**合法的 0 字节文件**，
   与"探针失败"无法区分；任何拿 `stat`/字节数判成功率的脚本都会把慢启动记成"跑出了空数据"。
   做法：写 `.tmp` → 校验 `rc==0` 且非空 → `mv` 落地。

### 4.1 另外两个坑是我自己代码里的（不同族，记下来免得下一个人重犯）

上面三条都是"环境骗了我"；这两条是"我骗了自己"，而且都不报错。

1. **自检里断言"未变异的代码应该出错"，等于没测**：我给布局评估写了自检，断言
   "320x240 / 500% 下应该有控件越界"——它红了，因为规划器**正确地**做了夹取。
   断言未变异代码的行为不是灵敏度测试，**必须先变异，再看检查是否变红**。
2. **变异选错，看起来像检查坏了，其实检查是好的**：改成变异之后，我第一次选的是"去掉宽度 clamp"
   （`rect.w = room`），它**仍然全绿**——因为 `room` 本身已经被 `client_w - margin - cx` 限住了，
   这个变异在数学上不可能造成越界。真正做约束的是游标上限 `cx = min(x, client_w)`。
   换成"去掉游标上限"这个变异才变红。现在宽度 clamp 那个变异作为"记录但不要求"列在 json 的
   `mutations_recorded_not_required` 里，并附一句说明，免得下一个人去"修"一个本来就没坏的东西。

### 4.2 行号会随提交漂移，而"引用行号"本身不带校验（本轮实测两处）

`n15-layout-eval.json` 的 `dpi_split.q1` 第一版里写着 `native/src/main.cpp:1702-1705`。那是我从 `a901ece` 抄的，
而 `83657f1`/`6dd853e` 各往 `main.cpp` 前面塞了代码，同一个 `SetProcessDpiAwarenessContext` 块现在在 `:1802-1805`。
**那份 JSON 当时的判定是对的、行号是错的**——判定与证据错开，读者按行号去翻会翻到别的东西。
同一次复核还抓到本文件自己写的 `:1803-1806`（差一行）。

处理：脚本里那串 evidence 改到 `:1802-1805`，docstring 写明"第一版行号来自 a901ece，`83657f1` 把这块整体推后了约 100 行"，然后重跑。
读数与旧版一致（§2.2），说明**错的只是指针，不是结论**——但一条断在最后一跳的证据链，和没有证据一样不能用。

这类错不报错、不改读数、只让复核的人踩空，所以只能靠纪律：**引用行号必须当轮复核，不能从上一次报告里继承。**
