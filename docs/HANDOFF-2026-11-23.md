### 2.3 构建与铁律
- 构建：`bash build-target.sh <目标...>` 或 `bash build-cmake.sh`，产物在 `native/build-nmake/`。需要 VS2022 + Windows SDK + CMake 3.24+。
- **四条铁律**：
  1. 新源文件**先 `git add` 再构建**：身份戳读 git index，否则 D-90 构建身份检查会拒绝；临时放行用 `TF2_IDENTITY_ALLOW_UNTRACKED=1`。
  2. 改过或还原过的源文件要 **touch**：nmake 只看 mtime。`cp -p` 还原会把旧 mtime 写回去，nmake 就不重编，变异体一直留在二进制里。这是 11-22 大面积假红的主因。
  3. /W4 零警告，七个 /WX 目标不许压警告。`false && x` 写法会触发 C4127 → C2220，变异要写成 `!(x) && (x)`。
  4. 构建和截帧一律走 `tools/lockrun.sh <owner> -- <命令>`。`verify-all.sh` 自己会抢锁，不要再用 lockrun 包它，否则死锁。
- 其它坑：这台机器的 `diff/comm/paste/cmp/join/sha256sum` 是 WinuxCmd 垫片。它读不了 `/dev/fd`，进程替换会被读成 0 字节；`sha256sum` 还会吃掉 stdin。gate 里一律改用实体临时文件，`gate_lint.py` 会拦截这种写法。

### 11.14 发布脚本的两个「假通过」（2026-11-23 晚）：没身份也报 PASS、没推上去也报 PASS

- 第三次发布跑到最后一步才死：浅克隆出来的临时仓库**没有提交身份**（这台机器没有全局 `user.email`），`git commit` 报 `Author identity unknown` 直接中止；脚本没检查这个退出码，继续打印 `local publish commit: 98ddaeb`（那是 origin/main 的旧值），后面的 `git push` 于是 `Everything up-to-date`，最后仍打印 `PUBLISH=PASS 98ddaeb -> origin main`。**origin/main 一个字节都没动。**
- 三处修（`tools/publish-software.sh`）：
  1. 提交前从开发仓库读 `user.name` / `user.email`，取不到就退 `Ada` / `ada@local`（公开历史里每一笔都是这个身份），再用 `git -c core.autocrlf=false -c user.name=… -c user.email=… commit` 传进去；提交失败直接 `PUBLISH=FAIL (commit)`。
  2. `PUBLISH_COMMIT=$(git rev-parse --verify -q publish-tmp)`，为空或等于 `REMOTE_MAIN` 就 `PUBLISH=FAIL (no new commit to push)`——「没有新提交」不能再算成功。
  3. 推送后 `git ls-remote origin refs/heads/main` 必须等于 `PUBLISH_COMMIT`，否则 `PUBLISH=FAIL (origin main is …)`。**现在 PASS 的含义是 origin/main 真的前进了。**
- 第三次除最后一步外全部通过，可作为基线：`selected=285 overlays=3`、`checks: PASS`、`636 files changed, 22579 insertions(+), 353357 deletions(-)`、`published file count: 288`；`--depth 1` 的浅克隆把克隆耗时从 ~55 分钟降到 ~2 分钟。修好后**还没重新发布**。

### 11.16 A4 在场条与转向曲线（2026-11-23 夜里）：只在跟随时出现，也只在录像能证明的地方出现

- **需求**（设计文档 §9 第 1、3 条）：跟随某个玩家时，条子上多两层——每 tick 的视角转速（急转是又高又窄的尖，阈值线以上涂红）和在场条（绿=录像里这一刻他活着，灰=死了，空=这段录像里根本没有他的画面）。两条都**只在跟随时**画，因为不跟随就没有「他」。
- **数据没有第二次扫描**：`DemoMotionCensus` 多两份稀疏历史——`playerSpans`（entity → `vector<DemoTickSpan>`）和 `lifeEdges`（`{tick, entity, life}`），喂在已经存在的逐次写入钩子 `observeMotionProperty`（`native/src/demo_tick_audit.cpp:640`）里；那个钩子开头就以 `isPlayerClass` 早退，所以投掷物、物品、世界实体的写入进不来。上限 `kMaxPlayerSpans=4096` / `kMaxLifeEdges=65536`，满了记 `spansCapped` / `lifeEdgesDropped`，不静默丢。曲线读的是 `census.turnRates`——detector 判琥珀提示用的**同一份**向量，所以红条和提示不可能互相矛盾。产品侧 `--analysis-scan` 本来就会开 census（`main.cpp:5957`），新的开关是 `--hud-timeline-entity <n>`（负数=跟着镜头），探针是 `--timeline-view <entity>`。
- **在场怎么算，三个坑都是量出来的**：
  1. 第一版要求「观察到一条 life 边且 life==0 才算活着」，实测**每个实体** `aliveTicks=0`：TF2 录像里重生是**新的实体实例**，基线在 create 包里，而 create 包不进这个钩子，所以观察得到的 life 边**全都**是非零值。

### 11.17 A5 逐条复查（2026-11-23 深夜）：条子上能走一遍的复查

- **需求**（设计文档 §9 第 5 条）：从时间轴上的异常一条一条走过去，每一条都自动播一遍，播完停下来等你看。这轮把「机器 + 横幅 + 产品接线 + 探针 + 门禁」一次做完。
- **机器是纯模块**：`TimelineReviewMachine`（`native/include/timeline_hud.h`，实现从 `native/src/timeline_hud.cpp:713` 起）不进 D3D、不接窗口，六个相位 `Idle / Slow / Countdown / Hold / Normal / Wait`。进入一条：Seek(条目 tick − `kLeadTicks`) + 0.25x + 播放（Slow 领跑）→ 到条目 tick 前停住倒数 3/2/1（每格 `kCountdownStep` 1.02 s）→ 在条目 tick 上停 `kHoldSeconds` 1 s → 1x 播 `kNormalSeconds` 2 s → Wait 等你按下一个。机器只**排队**命令（`TimelineReviewCommand{Seek/Speed/Pause}`，由 `takeCommands()` 取走），动播放的是调用方——所以产品和探针共用同一套节奏，产品侧走已有的 `applyPlaybackRequest`（`source="review"`）。
- **领跑为什么是 100 tick**：第一版 `kLeadTicks = 200`，0.25x 下是 12 秒慢放；实测读起来像卡死而不是「准备」，改成 100 tick（66.67 Hz 下 1.5 秒演示时间、0.25x 下 6 秒墙钟），实测这一段 6,069 ms。
- **一个真实 bug（这轮唯一的逻辑错）**：从第 1 条按「下一条」进第 2 条时，`update()` 先跑、排队的 Seek 由调用方在**下一帧**才应用，所以新条目的第一次 `update` 读到的还是**上一条**的 tick（已在 `start−1` 之后），Slow 相位被整段跳过。修法：机器加 `slowArmed_`，`enterItem` 置 false，Slow 分支只在**真的看见**游标落在条目之前（`tick < start−1`）时才允许收尾；另加 `kSlowArmTimeoutSeconds = 20.0` 兜底，免得轴上的第一条（前面没有画面可播）把相位卡死。产品的帧序和探针一样（先 update 后 drain），所以这个错在产品里同样会犯。
- **横幅**（`composeReviewOverlay`，`timeline_hud.cpp:947`）：顶部一条 `x=12 y=6 h=22 w=clientW−24`，右侧五个 74x16、间隔 6 的按钮 `PREV / REPLAY / NEXT / AUTO / EXIT`，左边一句话（第几条 / 共几条 / 相位与倒数 / 这条是什么）。AUTO 常亮蓝（帧里 `(135,177,227)`），**自动连播打开时转绿**；EXIT 红（`(89,42,45)`）。形状仍走 `Renderer::HudPrimitive`，和条子同一套。
- **交互**：`VK_F12` 开关复查；`Esc` 退出并回到进复查前的 tick（`stop()` 排队 `Pause(true)+Seek(savedTick)`）；鼠标点横幅按 `hudTimelineReviewButtonAt` 分派（上一条/重播/下一条/自动/退出），点击先问横幅、再走原有播放分支，所以横幅不会误触时间轴。产品另有 `--hud-review <index>`（启动即停在某条，给门禁截图用）。
- **条目集合与条子同源**：机器吃 `setAnomalies()` 的**同一份**列表（异常 + 提示，服务器 tick），按报告的轴裁剪。这局 138 条里 19 条落在轴外（就是 §11.13 里 `after=19` 那批），所以横幅写 `items=119` 而条子画 138——**不是漏**；`main.cpp:6138` 的注释当场重写说明了这一点。
- **实测（探针 `--scan --motion-detect --match-timeline --review-check`，cp_snakewater `bb841c6d…`）**：`review-check items=138 valid=1 axis=7,64352`；`review-overlay x=12 y=6 w=1256 h=22 buttons=5 primitives=13`；五条 `review-button` 都命中自己、高 16；`review-miss above=5 past=5`。节奏：第 1 条 `start=end=20021`，Slow 6,069 ms 从 tick 19,921 起步，倒数 3/2/1 各 1,020 ms（6,086 → 7,106 → 8,126），停在 20,021 上 1,020 ms，1x 跑 2,057 ms，Wait 停在 tick 20,155；`review-nav action=next from=0 index=1 phase=slow`、`replay` 同条重来、`auto=1` 后 `review-auto from=1 to=2 ticks=20971`；`review-restore saved=1000 tick=1000 ok=1 active=0 phase=idle`。
- **产品实测**（1264x681，`--hud-review 5`）：`review: active=1 reason=argument index=5 items=119 savedPlaybackTick=0`；横幅行 `review active=1 index=5 count=119 phase=wait … start=21546 end=21546 auto=0 saved=10319 buttons=5 x=12 y=6 w=1240 h=22`，五条 `review-button index=N label=… x=850/930/1010/1090/1170 y=9 w=74 h=16`。对照组（不传 `--hud-review`）只有一行 `review active=0 … buttons=0`。
- **门禁** `timeline-hud-check.sh` 扩到 **11 节** → **TIMELINE-HUD=PASS，216 OK / 0 FAIL**（`.scratch/a5-gate2.log`）。新增第 10 节：探针的条目数/横幅几何/五个按钮命中/轴外点击不算按钮；一次完整驱动的相位顺序（`slow,countdown,hold,normal,wait`）、倒数 `3,2,1`、四段时长区间、`speed`/`paused`/`tick` 判据、三个导航动作、自动连播推进一条、退出恢复原 tick；然后**产品截图对**（同一 tick 同一份设置，只多一个 `--hud-review 5`）——两帧差异 27,280 px，**全落在横幅窗口内**（`outside=0`，bbox x 12..1251、y 6..27，正好是 clientW−24 宽的一条），条顶平均 `(69,74,89)`、条身 `(17,19,25)`，AUTO 蓝像素 1,122、EXIT 红像素 1,105、搬运键一个不蓝不红（≤ 5），横幅文字让近白像素比对照帧多 395。
- **这轮的坑**：
  1. **产品的 trace 行带时间戳前缀**（`41773.4 review active=1 …`），门禁拿 `^review ` 锚定就一条也匹配不到，连带五个按钮采样全空、直接算术报错；探针自己的行没有前缀。凡是产品 trace，grep 一律不锚定。

- **还没做**：人眼验收（0.25x 领跑那 6 秒的观感、五个按钮在 1264 宽窗口里的可读性、一句横排在长标题下会不会挤）；复查期间要不要在条子上把「当前第几条」也画出来。

### 11.19 H1 转播 HUD（2026-11-23 深夜）：给观众看的一条叠加层

## 11.24 2026-11-24 锁协议统一：同一把锁不要再有两套建法

**症状**（所有者那边报告，单线程跑基线门禁）：连续三次 `VERIFY-LOCK=FAIL (stale lock was reclaimed but .scratch/verify-all.lock came back; another run won the race)`，前一行是 `STALE-LOCK=RECLAIMED owner=unknown pid=none age=1795451778s reason=no-owner-file`；而且执行前锁目录**不存在**，`Get-CimInstance` 也查不到任何 bash/播放器/编译进程。

**根因**：同一条路径 `.scratch/verify-all.lock` 上并存两套协议。`verify-lock.sh`（被 `verify-all.sh:220-229`、`tools/lockrun.sh` 使用）走 vlock：owner/pid/winpid/nonce/started/heartbeat 六个文件 + 心跳子进程 + 回收时 `rm -rf`；而 `mutate.sh:22-33` 和 `viewmodel-animation-check.sh:296-304`（`--mutation` 且无父锁时）是**裸 mkdir**——建出来的是一个没有 owner 文件的空目录，恰是 vlock 判 stale 的形状。两者一撞，vlock 的 `rm -rf` 与对方的 `mkdir`/`rmdir` 交替执行，就成了「刚回收完目录又回来；另一个 run 赢了竞态」——而那个 run 根本不存在。

`age=1795451778s` 也不是量出来的：目录在「mkdir 失败」与「stat 取 mtime」之间被删掉，`vlock_age` 回落 0（epoch），age 于是变成当前 epoch 秒数（1.79e9），把一次 TOCTOU 印成了一个荒唐的年龄。

**复现**（已证）：临时目录里放一个 600 次的裸 actor（`mkdir` 成功→`sleep 0.004`→`rmdir`），与 `vlock_acquire` 循环对撞，第 **22** 次就打印出与报告逐字相同的两行；对照组 `hits=1 reclaimed=6 acquired=15`。

**修复**（共享基础设施，产品代码零改动）：
- `verify-lock.sh`：目录已消失时 age 打 `age=gone`，不再把回落 0 印成 1.79e9 秒；回收的 `rm -rf`+`mkdir` 改成最多 40 次、间隔 50 ms 的重试（回收是幂等的，输一个几十微秒的窗口不该废掉整轮），全败才 FAIL 并打印 `attempts` / `entries`。
- `mutate.sh`：裸 mkdir/rmdir → `. ./verify-lock.sh` + `vlock_acquire "$LOCK_DIR" mutate 900`，失败仍打印原来的 `MUTATION-LOCK=FAIL (another build or mutation owns …)` 并 exit 2；EXIT trap 改 `vlock_release`。
- `viewmodel-animation-check.sh`：新增 `BUILD_LOCK_DIR=.scratch/verify-all.lock` 并 source verify-lock.sh；restore 里的裸 `rmdir` 改 `vlock_release`，`--mutation` 的裸 `mkdir` 改 `vlock_acquire "$BUILD_LOCK_DIR" viewmodel-animation 900`（失败仍打印原来的 `VIEWMODEL-ANIMATION=FAIL (a build owns …)`）。

**验证**：`bash stale-lock-selftest.sh` → `STALE-LOCK-SELFTEST=PASS assertions=30`（L5「刚建的空目录必须立刻以 no-owner-file 回收」仍然成立，所以**没有**给空目录加 grace 等待）；`tools/lockrun.sh smoke-owner -- true` → ACQUIRED + RELEASED、rc=0、事后无残留目录；竞态回归 `.scratch/repro-lock-race2.sh` → `RACE-TEST ok=8 stale_reclaims=6 race_failures=0`（未修时同形状第 22 次就失败）。

**规矩**：要这把锁就走 `vlock_acquire`（或 `tools/lockrun.sh`；在 chain 里则由父进程持锁并导出 `VERIFY_ALL_LOCK_HELD=1`）。**不要**再裸 `mkdir .scratch/verify-all.lock`，也不要对别人的锁目录 `rmdir`。

**踩坑**：复现脚本在本会话默认的 msys bash 里会挂住（命令替换要等 heartbeat 子进程关掉管道，和 `stale-lock-selftest.sh` 头部记的是同一个坑），必须用 `/c/Program Files/Git/bin/bash.exe` 并套 `timeout`。
