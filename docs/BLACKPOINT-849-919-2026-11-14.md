### 1.2 draw-path 一致的判定

`--world-texel` 和 `--world-albedo` 是**同一条 draw**、同一个 PVS、同一个 batch、同一份顶点缓冲，**只差 pixel shader 的一个返回分支**：

- `native/src/native_renderer_shaders.cpp:191` `sampledTexel = texture0.Sample(...)`
- `:195-197` texel 分支 `return float4(sampled, 1.0);`（在 blend / colour 之前）
- `:234` `float3 albedo = lerp(colour.rgb, sampled * colour.rgb, colour.a);`
- `:277` albedo 分支 `return float4(albedo, 1.0);`

两者之间的**全部**语义只有两项：

1. `:212-233` 的 WorldVertexTransition blend：需要顶点 `blend >= 0`。该材质 VMT 无第二层，trace 打的是 `blend=none`，且 `native_renderer_world.cpp:725-728` 只在 `blendedMaterials` 命中时才写 `a.blend = triangle.aAlpha`，否则保留默认 `-1`（`native/src/renderer_internal.h:24`）。→ **不成立**。
2. `:234` 的 `colour.rgb` 乘子。

所以：**同像素 texel=84 / albedo=0 ⇒ `colour.rgb` 在该片元为 0**（`:234` 里 `sampled*colour.rgb` 与 `colour.rgb` 两支都含 `colour.rgb`，与 `colour.a` 无关）。这一步是 draw-path 一致测出来的，不是从"albedo 黑"倒推的。

### 1.3 "数据来源"：BSP 没有这个字段；本树也没有 0 的写入点

- BSP v20 **没有** vertex colour lump。`native/include/bsp_map.h` 的 `BspTriangle`（`:11-70`）没有颜色字段；`native/src/bsp_map.cpp` 全文没有任何 colour 读取（grep `colour|color` 只命中 fogcolor）。所以"**BSP/displacement 顶点色数据本身就是 0**"这一条**被否掉**：没有这份数据。
- 渲染器是**自己合成**顶点色的，只有下面这些写入点，**全部非 0**：
  - `native/src/native_renderer_world.cpp:110` `convert()` 默认 `0.62,0.65,0.68,1.0`
  - `:124-126` 单材质 overload：`shade = 0.78 + (hash%23)/100`
  - `:664-665` atlas overload 的 tiled 分支：`r=g=b=1.0f`，`a=1.0f`
  - `:837` atlas overload 的 untiled 分支：`shade`（alpha 0）
  - `:133` / `:842` **仅** `--world-refused-mask` 时写洋红
  - `:883-885` **仅** `--world-face-id` 时写 face index（face 0 才会写出 (0,0,0,1)）
  - 输入布局 `native/src/native_renderer.cpp:353-367` 与 `WorldVertex`（`native/src/renderer_internal.h:17-27`）偏移逐字段核对一致（COLOR0 @12，uv @28，normal @36）。

**结论：本树无法产出 tiled 三角形的 0 顶点色**。所以 PHASE-F 里"vertex colour 0"这个读数在**现象层**是成立的（§1.2），但**根因**在本树里找不到落点，必须保留 OPEN。缺的那一步很具体：**COLOR0 的实际回读**（见 §4）。

### 1.4 语义：这个像素**不是**"正确的黑"

- Source 的 `LightmappedGeneric` 没有"顶点色 × albedo"这一项；世界材质的逐顶点颜色只有 WorldVertexTransition 的 blend 因子，而本 pass 已经用单独的 `blend` 属性建模（`world.cpp:725-728` + `shaders.cpp:212-233`）。所以 `colour.rgb` 本应是永久的 1。
- 本代码库自己两处写明了"缺省 tint = 白，不是黑"的约定：
  - `native/src/native_renderer_shaders.cpp:916-919`（`$phongtint` 缺省取白，注释说取黑会"删掉高光并看起来像 shader 正常"）
  - `native/src/native_renderer.cpp:224-226`（tint 是 fallback 颜色，**不是** albedo 的乘子）
- 因此 `:234` 把 `colour.rgb` 当乘子、且没有"0 视为中性"的回退，本身就是一处产品侧语义偏差；它平时不可见（白=无损），只有在本故障里暴露。**按 Source 语义这个像素是错的**，不能记成"正确黑"。

### 1.5 状态

**机制 PASS（draw-path 一致）；根因 OPEN。**
缺的证据：三角形 60275（face 17804）两个顶点在 GPU 里实际拿到的 COLOR0（以及 `blend`）；没有它就无法区分"上传写错 / 缓冲读到别的顶点 / 别的 draw 覆盖了该像素"。

## 2. 点 919,379：trace 与 draw 在哪一步分叉

### 2.1 先排除"face 选错"

用三份独立信息交叉，trace 的三角形选得**是对的**：

1. **离线复算 ordinal → face**（`.scratch/blackpoint/triorder.py`，按 `bsp_map.cpp:739-1180` 的 face walk + fan/displacement 规则复算）：
   - 复算总数 **69102**，产品自称 **68966**（trace `inputTriangles=68966`）→ 均匀高出 **136** 个三角形（若干被 parser 跳过的 face）。
   - 修正 136 后：`tri=60275` → **face 17804**，`tri=60285` → **face 17808**，`tri=19539/19538` → **face 6343**（face 6343 之前没有 displacement face，复算值本来就不需要修正）。
2. **既有 face-id 帧**（`.scratch/map-sultry-face-id/frame.bmp`，同相机 `-600 -600 950 20 45`，`--world-face-id`，但 `--no-world-vis` + 51 个 entity，**不是同一次 draw**）：解码 `r + g<<8 + b<<16`
   - 849,396 → **17804**；873,366 → **17808**；919,379 → **6343**；902,385 → **6343**（四个都精确等于编码值）。
3. 三个点（17804 / 17808 / 6343）的材质在 BSP 里都是 `METAL/METALGRATE013A2`，和 trace 的 `material=` 一致。

→ **trace 与光栅器在"这个像素归哪个 face"上一致**。所以 919 不是"trace 选错三角形/选错面"。

### 2.2 真正的分叉点：像素归属 / UV→texel 这一步

同一条 draw 的两个视图（§1.2 的同一论证）在 919 给出**不同的 texel**：

- trace 预测：`texel=82,81,79 texelA=255 uv=0.54595,0.53106`（`out3/face.trace:47854.9`）
- draw 实测：`texel.bmp` = **210,208,197**，`albedo.bmp` = **210,208,197**，`face.bmp` = **210,208,197**

`--world-texel` 返回的是"这个像素**实际被画的那个片元**"的 t0 采样（`shaders.cpp:195-197`），所以 210 是 draw 的答案，82 是 trace 的答案，两者不同 ⇒ **trace 在这个像素上指的不是被画的那个片元**。

同面相邻像素 902,385（face 6343 的另一个三角形）trace 预测 64,64,63，实测 64,64,62 —— **一致**。所以分叉不是材质、不是 tile、不是 UV 归一化公式（`main.cpp:8746-8760` 的 `mapTileCoord` 与 `world.cpp:715-720` 的 `worldTileCoord` 实现逐行相同，含同一个 `+0.5`），而是**这个像素本身的覆盖/归属**。

深度不能帮忙：`depth=0.9927`（trace 的三角形）比 `frameDepth=0.9931`（缓冲里的）**更近**，但该面是 `$translucent`（texelA=255 但材质 blended，depth-write 关，`shaders.cpp:386-387`），depth 缓冲里保留的是它后面的不透明面。所以"帧深度比 trace 深"既不证明也不否证。

### 2.3 分叉所在的决策点（文件:行）

| 决策 | trace 侧 | draw 侧 |
|---|---|---|
| 谁是 owner | `native/src/main.cpp:8625-8634`：屏幕空间边函数 + `area > 0` 判正面 + **`w < -1.0e-4f` 负容差**接受像素外侧的片元 + 自己比 depth | 光栅器：像素中心 + D3D top-left 填充规则 + 固定点，使用 `D3D11_CULL_BACK`（`native/src/native_renderer.cpp:678`）或 nocull（`:696`） |
| 哪些 pass 参与 | 只遍历 `displayMap.triangles`；**跳过 water**（`main.cpp:8616`）；**完全不含 entity/model**（`main.cpp:8493-8600` 只走 world 三角形） | 之后还有 entity pass（`native_renderer_frame.cpp:698-740`，用同一 pixel shader，`colour` 来自模型顶点色）和水面 pass（`waterOnlyConstants.envFeatures.x=0`，不吃 debug view） |

也就是说：**trace 的"最近三角形"是 CPU 自算的覆盖判定；draw 的 owner 是光栅器 + 后续 pass。919 处两者给出不同片元（texel 82 vs 210），而 902 相同。** 这符合"像素落在细栏杆边缘 1 px 内 + 覆盖规则不同"或"该像素被 trace 不建模的 pass 覆盖"这两类原因之一；现有证据**不能**区分它们（见 §3 缺证据）。

### 2.4 使二者一致的最小改动（gate 侧，不改渲染行为）

1. **trace 行加一个字段** `face=%d`（`triangle.faceIndex`，`main.cpp:8918-8936` 的 format 串 + 一个参数）。`BspTriangle::faceIndex` 已存在（`bsp_map.cpp:1167`）。
2. **门禁加一条 draw-path 断言**：同一次运行里同时出 `--world-face-id` 帧，解码 `r + g<<8 + b<<16`，要求 `face == decode(faceid.bmp, x, y)`。
3. **把"texel 预测 == texel 帧"作为任何 material/uv 结论的前置条件**（`world-black-account-check.sh` 现在只在 849 上钉了 `texel` 帧，没有把它当归属判据）。这一条就会把 849 和 919 都拒绝为"attribution invalid"，而不是写成"vertex colour / face-trace UV 不一致"。

这三条都是读数侧改动，不动渲染器，也不需要重建 PASS 基线。

| 字段 | 来源 | 期望 |

| `face=`（新加） / `tri=` / `material=` / `texel=` / `texelA=` / `uvInside` / `depth` | `out/trace.log` | 849: `face=17804 texel=84,83,81`；919: `face=6343 texel=82,81,79` |

**PASS 条件（能关闭一个点）**

- 849 → PASS 的条件：`face==17804 ∧ decode(faceid)==17804 ∧ cover≠洋红 ∧ texel 帧==84,83,81 ∧ albedo 帧==0`。此时"黑由 `colour.rgb` 乘子产生、且该像素确由 face 17804 拥有"成立；再用新增的 `--world-vertex-colour` 帧读到 (0,0,0) 即可把根因也关掉（否则根因仍 OPEN）。
- 919 → PASS 的条件：`decode(faceid)==face ∧ cover≠洋红 ∧ texel 帧==trace texel`。三者同时成立才允许说"trace 的 uv 与 draw 一致"；否则结论必须是**"该点归属错误"**而不是"uv 不一致"。

**UNSUPPORTED（判定为不可归因）**

- `decode(faceid) != face`（trace 指的像素不是 draw 的那个面）；或
- `cover == (255,0,255)`（entity 拥有该像素）；或
- `texel 帧 != trace texel` 且 `face` 相同（像素 owner 在 trace 未建模的 pass 里）。

三条任一命中，就把该点写成 `UNSUPPORTED: trace attribution is not draw-path-consistent at this pixel`，**不要**再写成材质/uv 缺陷。

## 5. 这个结论不能证明什么

1. **不能**证明 849 的 0 来自 BSP 数据 —— BSP v20 没有顶点色 lump，`bsp_map.cpp` 不读颜色。也不能证明它来自"渲染器缺省 0" —— 本树 6 个写入点全是非 0。
2. **不能**证明 849 是一个"材质缺陷"或"纹理缺陷"。texel=84,83,81 且 alpha=255 是实测的。
3. **不能**证明 919 的 trace uv 本身错了。已证的只有：trace 的 texel 预测 ≠ draw 的 texel（同像素），同面邻点 902 一致。**owner 未定**，因此"UV 不一致"只是当前最省事的说法，不是证据。
4. **不能**外推到其它相机/其它 tick/其它地图。全部读数绑在 `-600 -600 950 20 45` + tick 0 + 这份 demo/BSP 上。
5. **不能**用 `.scratch/map-sultry-face-id/frame.bmp` 当作 draw-path 一致的 oracle：它是另一次构建（2026-11-12）、`--no-world-vis`（clipApplied=0，68966 三角形全画）、且画了 51 个 entity。它只用于交叉验证 ordinal→face 映射（三点精确命中），不能替代同一次运行的 face-id 帧。
6. **不能**说"frame 深度不匹配就说明不是半透明面"：`$translucent` 面 depth-write 关，`frameDepth` 保留的是它后面那一层；`depthMatch=0` 在这类点是预期。
7. **不能**证明 face-id 的 136 个三角形漂移原因。复算 69102 vs 产品 68966 的差值在三个点上恒定（17804/17808/6343 全部命中），但具体是哪些 face 被 parser 丢弃没有逐 face 核实。
