# N23 全树 /W4 与局部 /WX（2026-11-18）

`native/` 的 55 个编译目标从「7 个在 /W4、48 个在 MSVC 默认 /W1」变成 **55/55 全在 /W4**，
138 个 translation unit 在 /W4 下**零告警**；产品、`tf2_core` 与五个协议/评审探针共 **7 个目标**再加 `/WX`。
顺手修掉告警门禁自己的一个路径 bug（它会把一棵干净的树报成 13 个 NEW），并把基线重出为空。

这份报告回答的是「警告等级覆盖到哪、原来的告警去哪了」。它**不**把 N23 标成完成：
N23 剩下的（代表目标零新增告警的看板、E3b batch 2 的其余部分）在任务清单里仍然 OPEN。

2026-11-19 追加两节：身份门禁在干净树上转成 PASS（§7），MSVC `/analyze` 已在 81 个 TU 上测过一轮（§8）；
sanitizer 因当前工具链缺 x64 ASan 运行库而没有读数，故障注入仍未开始。

## 1 依据与测量口径

任务清单的授权原文（`docs/PROJECT-NEXT-TASKS-2026-11-14.md:415`）：

> 输出 product/core/probe 的 /W4 覆盖矩阵与现有告警分类；分目标补，清理后再局部 /WX。

验收口径（`docs/PROJECT-EXECUTION-ROADMAP-2026-11-15.md:147`，E3b/N23）：
「代表目标零新增相关警告；故障被具名处理、有效路径不退化；全目标覆盖另列」。

三条测量前提，缺一条读数就会变成别的意思：

1. **没写 `/W` 的目标不在 /W3 上**。`docs/arch-ci-2026-11-14/N23-WARNING-COVERAGE.md` 记的是
   `CMP0092` 为 NEW 之后 CMake 不再追加 `/W3`，所以「没开 /W4」= MSVC 默认 `/W1`。改前那 48 个
   目标不是「差一档」，是基本只有 /W1 的诊断。
2. **覆盖要看 `flags.make`，不看 CMake 源、更不看注释**。一个目标可能在多个模块里被
   `target_compile_options` 追加参数；唯一的事实是 `native/build-nmake/CMakeFiles/<t>.dir/flags.make`。
   本轮 55/55 的读数就是逐个 `flags.make` 数出来的。
3. **按 TU 算会误导**。改前按 TU 覆盖是 63.4%（`N23-WARNING-COVERAGE.md`），看起来「过半已覆盖」；
   病在长尾——48 个目标整片没有 /W4 诊断，而它们正是探针与门禁读数的产地。

## 2 改了什么：一个目录级开关，加两条显式例外

`native/CMakeLists.txt:63` 起新增一个 MSVC 专用块（在 `include(cmake/tf2-identity.cmake)` 之后，
此时目录里的目标已全部创建）：

1. `get_property(... DIRECTORY PROPERTY BUILDSYSTEM_TARGETS)` 取本目录**自己**的目标列表；
   跳过 `UTILITY`（`tf2_build_stamp`）与 `INTERFACE_LIBRARY`（`tf2_identity`），其余一律
   `target_compile_options(... PRIVATE /W4)`。
2. `TF2_W3_TARGETS`（CACHE STRING，当前空）：**按名字**把某个目标退回 /W3，例外必须写在记录里，
   而不是靠漏掉某一行。
3. `_CRT_SECURE_NO_WARNINGS` 给**每一个**目标（含 `tf2_core` 与产品）。理由见 §4.2。

为什么从目录属性取目标列表而不是手抄 55 个名字：`N23-WARNING-COVERAGE.md` 的结论就是
7/55 来自逐 feature 的白名单——第 49 个目标（下一个新探针）会静默落回 /W1，而且没有任何检查会发现。
一份目标名单副本会漂移，漂移就是 7/55 的成因；目录属性不会。

`/WX` 是目录级默认列表 + 一个 CACHE 追加项：

```cmake
set(TF2_WX_DEFAULT_TARGETS
  tf2_core tf2_demo_native entity_protocol_probe entity_message_fixture_probe
  hud_probe minimap_probe review_workspace_probe)
set(TF2_WX_TARGETS "" CACHE STRING "Extra targets compiled with /WX on top of TF2_WX_DEFAULT_TARGETS.")
```

#### 4.2.1 为什么 `_CRT_SECURE_NO_WARNINGS` 是全树，而不是探针专享

报告 `N23-WARNING-COVERAGE.md` §4.3 的结论是「7 条 C4996 是平台方言，正确做法是加 `_CRT_SECURE_NO_WARNINGS`
而不是换 API」。这一轮把这个定义从「探针」扩到**每个目标**，理由写进了 CMake 注释：

- 整棵树只有一条构建链：MSVC + Win32 + D3D11（`build-target.sh` 与 CMake presets 都只有这一条），
  警告建议的「可移植替代」（`getenv_s`/`fopen_s`）**把代码绑死在 MSVC 上**，换不来可移植性；
- 产品读环境开关（`TF2_NATIVE_* Dump` 诊断路径）、探针写文件，本来就是方言；
- 把方言写在**一个地方**，好过散在 11 个文件级 `#pragma`。

这不是「关掉一整类告警」：C4996 之外没有新增任何 suppress；某天有人在没有这个定义的 TU 里写出
C4996，门禁仍然会把它报成 NEW。

#### 4.2.2 一条真缺陷：标题 trace 把宽字符逐字截断

`main.cpp:8627` 原来是：

```cpp
traceFmt("title: %s", std::string(fullTitle.begin(), fullTitle.end()).c_str());
```

`std::string` 的迭代器对构造函数**逐 `wchar_t` 转 `char`**：非 ASCII（demo 路径/标题里完全可能有）
的每个码元被截成低 8 位，trace 文件里就是乱码；`<xutility>` 的 C4244 就是这次实例化报出来的。
修法是与仓库已有 idiom 一致的一次 UTF-8 转码（`logstf_panel.cpp:72` 的 `narrow()` 是同一写法）：

```cpp
const int titleBytes = WideCharToMultiByte(CP_UTF8, 0, fullTitle.c_str(), -1, nullptr, 0, nullptr, nullptr);
std::string titleNarrow(static_cast<std::size_t>(titleBytes > 1 ? titleBytes - 1 : 0), '\0');
if (titleBytes > 1) {
  WideCharToMultiByte(CP_UTF8, 0, fullTitle.c_str(), -1, titleNarrow.data(), titleBytes, nullptr, nullptr);
}
traceFmt("title: %s", titleNarrow.c_str());
```

窗口标题（`SetWindowTextW`）没有动，所以画面与门禁读的 title 语义不变；变的只有 trace 那一行在
非 ASCII 下的字节。

## 5 /WX 的范围与理由

| 目标 | 为什么是它 |
|---|---|
| `tf2_core` | 改前就在 /W4，是全树被 include 最多的库 |
| `tf2_demo_native` | 产品：55 个门禁抓的帧都是它画的 |
| `entity_protocol_probe`、`entity_message_fixture_probe` | 协议/夹具探针：读数被其它门禁引用 |
| `hud_probe`、`minimap_probe`、`review_workspace_probe` | 改前 /W4 的评审面，输出直接进文档 |

其余 48 个保持 /W4、不进 /WX，是一个有理由的决定而不是遗漏：它们大多数是 **mutation 门禁的探针**，
其中若干个门禁会**故意**往探针里种可疑构造（改名、翻转符号、删检查）来证明检查能红；
`/WX` 会把「种进去的告警」变成**构建失败**，于是门禁红在一个跟断言无关的地方，真正的失败被掩盖。
探针是诊断程序，告警在那里是线索不是债务。

读数：`grep -l -- '/WX' native/build-nmake/CMakeFiles/*.dir/flags.make | wc -l` = **7**；
`/WX` 上线后 `bash build-target.sh all` rc=0、0 warning / 0 error。

## 6 告警门禁自己的 bug（`tools/warn-check.sh`）

修等级这件事如果没有门禁读数就是自说自话，而门禁这一轮先暴露了它自己的问题：

- worker（`tools/warn-check.sh` 里生成 `one.sh` 的那段）把 checkout 前缀**硬编码**成 `t105-e5`：
  `sed -e "s#^.*t105-e5/##"`。工作搬到 `t105-integrate` 之后前缀不再匹配，键保留了绝对路径，
  随后「外部头」规则把它改写成 `<external>/main.cpp:3149:C4996` 之类——于是基线里的
  `native/src/main.cpp:C4456` 显示 FIXED、当前告警显示 NEW。
- 修法：worker 从 `$1`（ROOT）派生前缀，`rootwin=$(cygpath -m "$ROOT")`，用 `sed -e "s#^.*${rootwin}/##"`。
  一个 worktree 改名不会再让整棵树「变红」。
- 影响：修复前 `--all` 读数是 `new=13 fixed=8 same=1`（**全是假象**）；修复后同一棵树
  `new=0 fixed=9 same=0`（9 个键 = 旧基线的 9 个 file:code 键，全部被本轮修掉）。
- 基线重出：树已经在 /W4 下零告警，`--emit-baseline` 产出**只有注释头、0 条数据**的
  `tools/warn-baseline.tsv`，表示「现有告警集合为空」；之后任何告警都是 NEW。
  `emit` 仍会在编译失败时拒绝写基线（原有关卡保留）。

读数（命令、日志都在仓库外）：

```bash
bash tools/warn-check.sh --emit-baseline   # WARN-GATE=BASELINE-WRITTEN lines=0 path=tools/warn-baseline.tsv
bash tools/warn-check.sh                   # WARN-GATE tus=138 / WARN-GATE=PASS new=0 fixed=0 same=0
bash tools/warn-check.sh --selftest        # WARN-GATE=SELFTEST-PASS planted=1 reported=1
```

基线重出之前，用旧基线跑 `--all` 的读数是 `WARN-GATE=PASS new=0 fixed=9 same=0`：
9 个键全部被本轮修掉、没有新增，这就是「全树零告警」的第二次独立读数（第一次是全量构建日志里的 0 行 warning）。

**第三个 bug（本轮被 /WX 逼出来的）**：`--selftest` 原先直接借 `tf2_core` 的 flags 编译种了告警的 TU。
`tf2_core` 在 §5 里进了 /WX 之后，那个「种进去的告警」变成 `error C2220`，worker 把它记成 `FAILED`，
selftest 于是报 `planted-warning-not-observed`——一个正确的 /WX 让一个正确的自检变红。
修法：worker 接受 `WARNCHECK_NO_WX=1` 时只对**这一次自检编译**剥掉 `/WX`（注释写明为什么），
门禁本身的编译仍然用目标原样的 flags。重跑：`WARN-GATE=SELFTEST-PASS planted=1 reported=1`。

  1. `TF2_NATIVE_TRACE` 被导出成 POSIX 路径（`/d/…`）。MSYS 只转换命令行参数、不转换环境变量；
     产品 `native/src/main_trace.cpp:84` 用 `GetEnvironmentVariableW` 读到无盘符路径，
     `_wfopen_s(..., L"w")` 静默失败（:85-86），9 条 trace 断言读到空文件。修法：`trace_win()`
     用 `cygpath -w`（`0d37539e`）。
  2. sidecar 与 provenance 由 CMake `file(WRITE)`（`native/cmake/write-identity-sidecar.cmake:150`）
     写成 CRLF（`grep -c $'\r'`：sidecar 15 行、`native/generated/tf2_build_stamp.identity` 12 行）；
     带 `$` 锚点的 `grep -cE '^exeSha256=[0-9a-f]{64}$'` 把 CR 当字符，4 条 sidecar 与 provenance
     `dirtyFiles` 断言读成 0。修法：读前 `tr -d '\r'`（同一个提交）。
  3. 产品写**两行** `args:`：`args: unrecognized=N first=… all=…`（`native/src/main.cpp:4954`）
     与 `args: refused switch count=N first=…`（`main.cpp:4988`）；未知开关加越界值同时出现时两行都在，
     旧断言「exactly one args: line」不可能过。修法：一行一条断言（`6c0ee43a`）。
- **没有**重跑 55 个默认路径门禁：这次改动的可观测面只有 trace 的 title 行编码与 0 处渲染逻辑；
  N17 报告 §5.3 已经记录 55 门在 4 路并发下的限制与串行定案成本，重跑它换不来新信息。
  如果后续有门禁在 /W4 下改变行为，那是门禁自己的问题，应该由该门禁的复跑证明。

## 9 没证明什么

1. **零告警不等于零缺陷**。C4996 是被刻意静音的方言（§4.2.1）：11 个站点仍应按代码读，
   尤其是 `getenv` 返回指针的生命周期（`main.cpp:15809` 在同一表达式里调两次是安全的，
   但别把它当作可存储的指针）。
2. **/WX 只覆盖 7 个目标**。其余 48 个目标新增告警仍然不会让构建失败，只会在运行门禁时变红。
3. **/W4 只覆盖 MSVC 的编译期诊断**。`/analyze` 本轮只做过一次人工 sweep（§8，不在门禁/CI 里）；clang-tidy、CodeQL 没有；链接期告警未计。
4. **第三方头的一条告警依赖工具集版本**。本机 `14.44.35207`；换 VS 版本后 `<external>` 的告警集合可能变化，
   本轮唯一一条（`xutility`）已随实例化修法消失。
5. **A5 类别告警没有被系统性审计**。本轮只保证「已有告警为 0」，没有按缺陷类（空指针/未初始化/
   数组越界之外的语义类）做抽样复核；那属于 N23 后面的工作。
6. **55 是编译目标数，不是门禁数**。门禁清单（`*-check.sh`）与目标不是一一对应，覆盖矩阵不回答
   「每个门禁都被 /W4 编译过一次」。
7. **单机单工具集单次读数**。没有在多台机器、多个 VS 版本上重复，也没有对同一份源码做两次独立全量构建的
   告警集合比对（增量构建的「0 warning」只代表这次真正重编的 TU）。
8. **`/analyze` 不在任何门禁里**。§8 的「51+30 TU、8 条」是一次性人工读数，不随提交更新，也不阻止新告警进入。
9. **C6262 只剩一处记录**。2026-11-19 把三处（`native_ui.cpp:70/76`、`settings_store.cpp:132`、
   `main.cpp:2287`）搬到堆；`wWinMain` 的 58,208 B 留给 N24 拆分。搬堆的收益仍没有量，
   `/analyze` 不在门禁里，「复测后三条消失」尚未证明。
10. **sanitizer 没有读数**。x64 ASan 运行库缺失，「记忆安全已检查」这句话本轮无证据；WinMM/D3D 故障注入同样未做。
11. **身份 PASS 只对这一棵树、这一个提交成立**（`head=aa8b0df0438d`，`dirty=0`）。换树/换提交要重跑；
    它证明的是产品会写出与源码一致的 identity 读数，不是身份链在所有环境下都对。
