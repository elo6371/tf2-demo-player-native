# N17 Player Animation: the idle cursor advances, and run/aim is a real blend - 2026-11-18

Card: `n17-anim` (branch `work/n17-anim`). This closes three of the four animation
gaps the 2026-11-17 Scout report left open -- stationary idle progression, multi-blend
sampling, and the "one trace frame cannot prove frozen versus advancing" objection --
and says plainly what it does not close.

| Item before this card | Reading now |
|---|---|
| A standing body's cycle never left 0 (`idleRate=0` by design) | Advances at the idle clip's own rate, `fps / frameCount` (Scout: 0.666667 cyc/s from a 45-frame, 30 fps `stand_PRIMARY`) |
| The sampler selected the first anim descriptor only | Locomotion blend of idle/walk/run plus an aim pose layer, normalised, weights in the trace |
| A single trace frame was the only pose evidence | Per-body `anim: frame` line (cycle, decoded frame, skin-matrix hash) every resolved tick, and four consecutive clock ticks in the probe |

## 1. The clock: idle advances at the clip's own duration

`native/include/animation_clock.h` now says, in the contract block and in code:

* `animationCycleRate(frameCount, fps)` returns `fps / frameCount` -- TF2's
  one-section-one-cycle convention -- and 0 when the timing is unusable.
* `AnimationClockConfig::idleRate` is the caller's field. The clock still refuses to
  invent a rate: the default 0 keeps the old frozen behaviour, which is the honest
  reading for a body whose idle clip is unknown.
* `advanceAnimationClock` reports `advanced` = `deltaCycle > 0`, keeps `dt = (tick -
  lastTick) / tickRate`, treats a repeated or backwards tick as no advance, and wraps
  the cycle into [0, 1).

`native/src/main.cpp` resolves the rate it passes: the idle descriptor's frame count
and fps go through `animationCycleRate` every time a body's clock is stepped, so no
frame count is hardcoded and every class table gets its own number.

## 2. The blend: idle/walk/run weights plus an aim pose layer

`native/include/animation_blend.h` (header-only, pure functions):

* `locomotionBlendWeights(speed, config)` -- a two-stage ramp over idle/walk/run that
  always sums to 1 (thresholds: idle<0.5, walk 150, run 300 units/s).
* `aimLayerWeightDegrees(viewYaw, bodyYaw, fullYaw=90)` -- how far the body faces away
  from where the view looks, wrapped, capped by `kAimLayerWeightCap = 0.5`.
* `normalizeBlendWeights` -- the one normaliser the sampler uses, so "sums to 1" is
  enforced rather than believed.

The cap is the design decision this card had to make: TF2's aim clips
(`PRIMARY_aimmatrix_idle`, `PRIMARY_aimmatrix_run`, ...) are ONE-FRAME poses. At weight
1 they would hold the locomotion cycle still, which is the defect this card exists to
remove. Capping the aim share at 0.5 keeps the locomotion cycle driving under the aim
pose, and the trace shows the aim rung capped.

`native/src/animation_binding.cpp` gains the multi-layer request path: the caller pushes
up to `kMaxBlendLayers = 4` layers (sequence, cycle, weight); the sampler samples each,
drops unusable ones with a reason and a counter, lets the heaviest surviving layer
supply the reported frame/frameCount/localFrame/sectionFrames, normalises the weights,
and blends the local poses -- positions linearly, quaternions sign-aligned to the
reference layer then weighted and renormalised, falling back to the single sample with
a reason if the blend cannot be built. Single-sequence callers (weapon attach, crouch,
flinch) take the same code path with zero layers and stay bit-identical.

Sequence picking extends `animation_sequence_match.h` with two pickers that the generic
matcher deliberately cannot express: `chooseWalkSequence` (needs a real walk cycle,
rejects airwalk/crouch/swim/one-shots, returns -1 when the table has none) and
`chooseAimMatrixSequence` (needs `aimmatrix` + idle/run, one-frame poses allowed,
rejects crouch/stun). Scout has no standing `walk_PRIMARY`; its walk rung therefore
reuses the run cycle and the trace says `walkFallback=1` rather than inventing a clip.

## 3. Trace: three lines that make the claim checkable

* `anim: pick` -- per model: `idleSeq/idleLabel movingSeq/movingLabel walkSeq walkLabel
  aimIdleSeq/aimIdleLabel aimMoveSeq/aimMoveLabel`, printed once when the choice resolves.
* `anim: blend` -- per body per tick: `state speed rate cycle idleRate viewYaw bodyYaw
  idle/walk/run/aim weights sum seqs walkFallback layers dropped appliedSum
  blendReason`.
* `anim: frame` -- per clock-driven body per tick: `seq frame/frameCount localFrame
  sectionFrames cycle frameAdvanced poseChanged poseHash`, where `poseHash` is FNV-1a
  over the skin matrices the draw is about to use. `frame/frameCount` is the heaviest
  surviving blend layer's decoded frame, and `seq` is the sequence the request names;
  when the capped aim pose is the heaviest (weight 0.5 against a 0.5 locomotion share)
  the decoded frame is the aim pose's single frame, which is why the cycle and the hash,
  not the frame number, are the advance witnesses.

Same-tick determinism was a real defect found by the trace: every scene update at one
tick re-measured the body heading, but only the update that saw an origin delta had one,
so the second update dropped the aim layer and the weights differed at the SAME tick.
The runtime now persists the last measured heading (`PlayerAnimationRuntime::hasHeading /
headingDegrees`) and every update at that tick reuses it.

## 6. What this does NOT establish

* No in-game TF2 pose comparison. The weights and rates are deterministic and
  documented; whether TF2's own blend tree produces these numbers is not tested here.
* The aim layer is a one-frame pose capped at 0.5, not TF2's 12-blend aim matrix.
* Scout's walk rung reuses the run cycle (`walkFallback=1`) because its table has no
  standing walk cycle; a class with one gets its own clip.
* Product-level IDLE windows are not observable on this demo: every resolved snapshot
  is 340-800 ticks apart and every body's origin delta clears the 0.5 threshold, so all
  26 post-baseline ticks classify as moving. Idle advance is therefore proven at the
  clock level (probe, four consecutive ticks, one-second integral) and by contract, not
  by a product trace line -- there is no idle window in the recording to read.
* Flinch/crouch layering is unchanged by this card and still takes the single-sample
  path.
