## 2 两个点分别是什么

### 2.1 849：几何对、着色黑

- GPU 画的 face **等于** CPU 预测（17804）。所以**不是洞、不是覆盖问题**。
- 同一像素 `texel=82,81,79`（非黑）、`albedo=82,81,79`、`expected=81,67,51`（非黑），帧却是 **(0,0,0)**。
- 结论：问题在**着色链**（顶点色乘子 / 光照 / 最终写入），与既有 849 归因方向一致，但没有 COLOR0 回读就无法再往下定一层。

### 2.2 919：oracle 与光栅器分叉，不是材质

- face-id 帧在该像素是 **16777215**，即该像素不属于任何 dface——是 sky/backdrop（`depthMatch=0` 与之一致）。
- 所以 919 的"预测 albedo=82,81,79 vs 帧=210,208,197"根本不是材质错，而是**CPU 点选中的三角形（6343）在 GPU 上没画到这个像素**。
- 这条否证了此前把它归入"黑像素/材质"的方向；它属于 **hole/覆盖 oracle 的精度问题**：点选三角与光栅化结果不一致。

## 12 更正：离线映射是可行的，§11 的结论作废

§11 说"face-id 不是 dface 索引，离线映射行不通"——**错**。原因是 BSP 的 lump 是 **LZMA 压缩**的，我按未压缩读，才得到 4477 条；解压后是 **21289** 条，与产品面表一致。工具已修，映射成功。

`tools/bsp_face.py` 的读数（`cp_sultry_b8a`，`decoded_faces=21289`）：

| face | 材质 | 尺寸 | dispinfo | 边数 | plane | side |
|---|---|---|---:|---:|---|---:|
| **6343** | `METAL/METALGRATE013A2` | 256×256 | **-1（非位移）** | 4 | (0,-1,0)@**-58.00** | 1 |
| **15566** | `SULTRYPROPS/GOTHIC_FENCE` | 512×256 | **-1** | 4 | (0,-1,0)@**-4.49** | 1 |

两个错点的结论因此改变：

- **都不是位移面**，"位移 fallback 被丢弃"的假设**排除**；

## 16 选中三角形的屏幕坐标：oracle 的三角形在光栅帧里是空的

新增 `triScreen=` 字段（诊断，见 §17）。同相机读数：

| 点 | oracle 选中的三角形三个角 | 点是否在内 | 该三角形内部各点的 frame id |
|---|---|---|---|
| 919,379 | (950.25,333.08) (906.16,433.14) (884.18,424.54) | 是（w=0.50/0.10/0.40） | **(919,379) / (913,396) / (930,360) / (900,420) / (940,350) 全部 = 16777215** |
| 849,396 | (858.54,339.76) (849.93,416.24) (836.08,410.71) | 是 | 帧 id = 17804（有面），但颜色是黑 |
| 500,400 | (389.00,204.12) (603.39,551.50) (437.44,373.82) | 是 | 16777215 |

三件事可以同时成立：

1. oracle 的三角形**确实覆盖**该像素（手算重心坐标全为正，不是边界情形）；
2. 该三角形对应的面 6343 在 id 帧里**有 781 个像素**（bbox 与三角形 bbox 基本吻合：x884..948 / y329..432 vs 角点 x884..950、y333..433）；
3. 但三角形**内部采样的 5 个点全是"没有世界面"**，包括重心。

781 px 只占该三角形面积（约 1289 px）的 60%，也就是说**这个三角形是被部分绘制的**，缺的那 40% 恰好是我们采样的位置。

这说明 oracle 的模型少了一层：它在世界里找最前面的三角形，却没考虑**不写 face id 的那些绘制**（道具/天空遍）。有两种可能，本轮没有区分开：

- 若这些像素上盖着道具（道具遍不写 id），则 919 的 id 应该是 6343 而不是 16777215 —— 与实测矛盾；
- 若该三角形在光栅化时被整体剔除了一部分（例如按 leaf 的逐面剔除），则 id 会缺，而 oracle 因为只看 `worldVisKeptIndices` 之外的可见性判据仍保留它。

**因此下一步不是改渲染器，而是给 oracle 补两件事**：把"该像素是否被非世界绘制覆盖"和"该三角形是否真的进入本轮 draw call"变成读数。`triScreen=` 已经把几何侧的数据备好。

## 19 收敛到什么

剩下的解释只有一个：**oracle 的屏幕投影与 GPU 的实际光栅结果对同一三角形给出不同的像素覆盖**。

- 三角形的顶点、序数、是否进入索引缓冲、顶点色、深度比较函数，全部已排除；
- 三角形在 id 帧里被绘制了 60% 的面积，缺的 40% 正是采样点所在；
- 10/12 的网格点完全吻合 —— 说明差异不是全局常数偏移，而是**边界附近**的判定差。

要在不猜的前提下再往下走，需要一次 **GPU 侧读数**：把该三角形的边函数/重心坐标渲染进一个调试通道，与 oracle 的 CPU 值逐像素比对。这需要新的调试视图（产品改动），不是再加一个 trace 字段能解决的。

**因此地图缺陷（D03）保持 OPEN，本轮把它从"黑点/材质问题"收敛成"CPU 与 GPU 的覆盖判定不一致"，并留下了 10 条已排除假设与对应证据。**

## 24 关键发现：我们采样的帧不是被隔离的那次世界绘制

绘制时刻读数（新增 `world draw branch` 行）：

| 运行 | `batchesIndexed` | `indexCount` | `batchDrawCalls` |
|---|---|---:|---:|
| `--world-triangle 19539` | 1 | **3** | 1 |
| 不隔离 | 1 | 129,015 | 7 |

索引只有 3 个、批次只画 1 次——**绘制确实按 3 个索引走了**。但同一配置下的帧：

| 运行 | 非背景采样 | (919,379) 颜色 |
|---|---:|---|
| 只画 1 个三角形 | 215,202 / 214,880 | (210,208,197) |
| 画整个世界 | 213,802 / 214,880 | **(210,208,197)** |

**两次的像素完全一样**，而且画 1 个三角形时屏幕依然是满的。

结论：**抓到的这一帧不是那次世界绘制的输出**。它来自另一个覆盖全屏的 pass（天空盒/背景/雾，或刷模型的独立 draw），世界 draw 无论画 3 个索引还是 129k 个，都不改变这一帧。

这直接推翻了此前建立在"帧像素"上的推理链：

- **849 的"帧是黑"、919 的"帧是浅灰"** —— 不能据此判断世界面画没画到；那个颜色可能根本不由世界 pass 产生；
- 之前"781 px 属于 face 6343"的统计来自 face-id 帧，而 face-id 帧同样可能来自另一个 upload（`setWorldFaceIdUpload` 是上传期开关，天空/id 有自己的缓冲）；
- 因此 §7 的 10/12 网格对照，其"光栅 id"一侧的**来源**也需要重新确认。
