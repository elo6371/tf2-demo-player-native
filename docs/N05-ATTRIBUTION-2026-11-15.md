# N05 归因第一步：849 与 919 的实际绘制路径 - 2026-11-15

- 输入：`cp_sultry_b8a` STV、tick 0、`--debug-camera -600 -600 950 20 45`、`--world-sky`、1280×720（与 `world-black-account-check.sh` 同参数）
- 三次运行：`--world-hole-trace`、`--world-face-trace`、`--world-face-id`（同一 exe `cfcdbe5d…`）
- 结论：**919 不是黑点，也不是材质问题；它是一块 sky/backdrop 像素**。849 的几何覆盖是对的，黑来自着色路径。

## 2 两个点分别是什么

### 2.1 849：几何对、着色黑

- GPU 画的 face **等于** CPU 预测（17804）。所以**不是洞、不是覆盖问题**。
- 同一像素 `texel=82,81,79`（非黑）、`albedo=82,81,79`、`expected=81,67,51`（非黑），帧却是 **(0,0,0)**。
- 结论：问题在**着色链**（顶点色乘子 / 光照 / 最终写入），与既有 849 归因方向一致，但没有 COLOR0 回读就无法再往下定一层。

### 2.2 919：oracle 与光栅器分叉，不是材质

- face-id 帧在该像素是 **16777215**，即该像素不属于任何 dface——是 sky/backdrop（`depthMatch=0` 与之一致）。
- 所以 919 的"预测 albedo=82,81,79 vs 帧=210,208,197"根本不是材质错，而是**CPU 点选中的三角形（6343）在 GPU 上没画到这个像素**。
- 这条否证了此前把它归入"黑像素/材质"的方向；它属于 **hole/覆盖 oracle 的精度问题**：点选三角与光栅化结果不一致。

## 3 与台账的关系

- **D03**：不再笼统记"849/919 两个黑点"。改为两条独立条目：
  - 849 → **着色链**（有几何、帧黑、texel 非黑）；
  - 919 → **oracle/光栅分叉**（帧是 sky，与预测面无关）。
- 两者都**仍 OPEN**：849 缺 COLOR0 回读，919 缺"为什么点选 6343"的最小复现（同一像素在点选里指向的三角形，其屏幕投影是否真的覆盖该像素）。
- **不关闭 D01**：七图矩阵仍只有 2/14 格。

## 6 追加对照：919 不是被 cull / vis-clip 拿掉的

同一相机、同 tick、同一 face-id 视图，各关一个开关读 919,379：

| 运行 | 919,379 的 face-id | 判定 |
|---|---|---|
| 默认 | 16777215（sky） | — |
| `--no-world-cull` | 16777215 | **不是 cull** |
| `--no-world-vis-clip` | 16777215 | **不是 vis-clip** |

所以三角形 6343 既没被剔除也没被裁掉，而是**点选本身指错了**：CPU 的点→三角形判定认为该像素属于 6343，光栅器认为不属于。剩下的可能只有两种：点在三角形边上（填充规则差异），或点选用的投影与光栅化差了一点（缩放/偏移）。

要区分这两者，需要 6343 的**屏幕坐标**。现有 trace 只有 `tri=`、`depth=`、`uv=`，没有屏幕顶点；`world_geometry_probe --face-info 6343` 能给面/平面/范围，但要自己投影。这是**下一步唯一需要的证据**，且可以完全离线做（不跑产品）。

## 7 网格对照：错误是逐点的，不是全局投影偏移

12 个点、同一相机/tick，用 `--world-hole-trace` 的 `drawn=face=` 与 face-id 帧逐点比：

| 点 | oracle face | 光栅 id | 判定 |
|---|---:|---:|---|

| 500,200 | 14026 | 14026 | OK |
| 800,200 | 20637 | 20637 | OK |
| 1100,200 | 12123 | 12123 | OK |

| **500,400** | **15566** | **16777215** | **MISMATCH** |
| **919,379** | **6343** | **16777215** | **MISMATCH** |
| 1100,400 | 6159 | 6159 | OK |
| 200,600 | 11280 | 11280 | OK |
| 500,600 | 11292 | 11292 | OK |
| 800,600 | 3222 | 3222 | OK |
| 1100,600 | 6387 | 6387 | OK |

**10/12 精确一致**，2 个不一致且**都落在 16777215（sky/未着色）**。

结论：

- **不是**投影整体偏移——若偏移，10 个 OK 不可能全对；
- **是逐点的点选错误**：oracle 的首次命中三角形在该像素上根本没被画出来；
- 两处错点都表现为"oracle 说有几何、帧里是天空"，与 919 的 `depthMatch=0` 同源；
- `--no-world-cull` / `--no-world-vis-clip` 都改不动它（§6），所以不是剔除/裁切。

**这正是本卡的归因**：919 与 500,400 属于同一类——**oracle 选中了光栅器不画的三角形**（位移面 fallback、天空遮挡或 pass 归属三者之一，尚未区分）。下一层只需要一个读数：这两处三角形所属的 face 是否被渲染器拒绝/归类为 sky。`--world-refused-mask` 本轮跑过但没有对应的 trace 行（只有 hud/logstf 的 refused），需要先确认该开关的输出通道。

## 10 天空遍判定：919 下面没有世界几何

同相机、同 tick，face-id 视图三种几何过滤：

| 运行 | 919,379 | 500,400 | 849,396 |
|---|---|---|---|
| 默认 | 16777215 | 16777215 | 17804 |
| `--world-geometry sky`（只画天空面） | 1446414 | 1446414 | 1446414 |
| `--no-world-sky` | **16777215** | **16777215** | 17804 |

- 关掉天空遍后 919 仍是 16777215（clear），说明**世界几何在该像素什么都没画**；
- 只画天空面时整屏都是 1446414，说明天空面在另一趟里画、且不写 face id；
- 因此 919 的最终颜色来自**天空遍**，不是某个世界面。

结合 §7 的 10/12：oracle 在这两个像素上选中的三角形，光栅器既没画、天空遍也没让位——**是点选本身错**，与材质、cull、clip、天空遮挡都无关。剩下的唯一入口是给 oracle 打印选中三角形的屏幕坐标（产品诊断字段）。

## 11 负结果：face-id 不是 dface 索引，离线映射行不通

为了不跑产品就查清 6343/15566 是什么，写了 `tools/bsp_face.py` 直接读 BSP 的 dface/texinfo/texdata。结论是**这条路不通，但原因本身有用**：

| 项 | 值 |
|---|---|
| `cp_sultry_b8a.bsp` 的 LUMP_FACES 条目数 | **4477** |
| 探针报告的 faces | **21289** |
| hole-trace 里的 `face=` 最大值 | 21288 |

所以产品在 trace 与 face-id 帧里用的 `face=` **不是 dface 索引**，而是它自己的面表（含位移展开）。拿 BSP 的 dface 去对 6343/15566 会得到完全不同的东西，**不能用**。

含义：

- 想离线对账，得先让产品把它的面表导出来（一条 dump），这也是下一步要的那个"最小实际 draw 诊断"的一部分；
- 在那之前，任何"这个 id 对应哪个 dface"的推断都是错的——本文件不作这种推断。

`tools/bsp_face.py` 保留：它对 dface 级问题（材质、位移、surface flags）仍然有效，只是不能用来解释 face-id 帧。
