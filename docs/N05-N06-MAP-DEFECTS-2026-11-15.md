### 2.3 与光栅器的共同点与分叉点

共同点（同一份数据）：displayMap.triangles、同一条 MVP、同一个 worldHorizontalScale/Center/MinZ/SpanZ、同一个 tile 计划与同一张 atlas 描述。

分叉点（各自一套）：

1. 覆盖判定：trace 用自己写的边函数，光栅器用 D3D 的扫描转换。
2. 背面剔除：trace 用 `area > 0.0f` 的屏幕空间判定（main.cpp:8875），光栅器用 D3D11_CULL_BACK / nocull（native/src/native_renderer.cpp:678、696）。
3. pass 集合：trace 只走世界三角形，跳过 water（main.cpp:8868），不包含 entity、不含 ViewModel、不含水面/标记/天空这些后画的 pass。
4. 深度：trace 自己算 depth，只在最后拿 depth buffer 对账一次（8903-8911）。

### 2.4 trace 自带的对账字段在本构建里不携带区分信息

face.trace 里 7 行 `point=`，其中 6 行带 depthMatch（第 7 行是 `tri=none reason=no-drawn-triangle`，main.cpp:8894）。实测：

    $ grep -c "depthMatch=1" face.trace    -> 0
    $ grep -c "depthMatch=0" face.trace    -> 6

即 6/6 全部 depthMatch=0。三行原文（原样引用，只截 vtf 之后的部分）：

### 2.5 判决与判据

判决：PASS（这一问已取证并有结论）。

判据：实现位置与调用点有文件:行号（main.cpp:8741-8742、12875）；它自己的投影/剔除/近三角形/pass 集合各有独立行号（8712、8776、8862、8875、8882、8868、8889）；它唯一读真帧的地方只读深度（8903、8910、8911）。
因此三选一的定性是：trace 既不是射线求交，也不是光栅器读回，是一份与光栅器共用输入、但自带覆盖判定与 pass 集合的 CPU 预测 → 919 不能只凭 trace 定性；口号式说法「trace 与光栅器对同一表面分叉」也不成立，因为两者选中的是不同面的可能性与 trace 深度模型本身的偏差在本轮无法分离（见 2.4 与 6 节）。

### 3.3 919,379 的实测像素与两条否证

919,379 在三个视图里的实测值（本轮直接解码 out3 三帧）：

| 视图 | 919,379 | 5x5 邻域 min/max | 唯一色数 |
| --- | --- | --- | --- |
| face.bmp | (210,208,197) | (207,204,193) / (216,214,202) | 15 |
| albedo.bmp | (210,208,197) | 同上 | 15 |
| texel.bmp | (210,208,197) | 同上 | 15 |

否证 1（值域）：该 VTF 任何 mip 的 max RGB ≤ 111，而三个视图在 919 都读到 (210,208,197)，全纹理精确匹配 (210,208,197) 的次数 = 0。texel 视图的语义是「t0 的原始采样、未经 blend/光图/光照」（native_renderer_shaders.cpp:191-197，注释在 193-194），所以 (210,208,197) 不可能是这张 VTF 的采样值。由此「产品把 alpha 当 1 画出亮白」不成立：亮白本身就不来自这张纹理。

否证 2（该 uv 处是空）:trace 报 uv=0.54595,0.53106，按 mip0 映射到 (139,135)，实测 (0,0,0,0) 全透明；按 3.2 表，mip1/mip4 在该 uv 读到 (90,88,86,255)，也与 (210,208,197) 无关。

否证 3（同一像素两份读数互相打架）：trace 在同一像素给的 texel 是 (82,81,79) texelA=255（face.trace:47854.9），而 texel 视图在同一个像素给的是 (210,208,197)，差 128。两份「这里采样到什么」的读数不可能同时描述同一个被画的表面。

否证 4（trace 的 texel 不是源 VTF 的 texel）：849 uv=0.53337,0.53179 → mip0 (136,136) = (0,0,0,0)，但 trace 报 texel=(84,83,81) texelA=255；919 同理（mip0 全透明，trace 报 alpha 255）。trace 的 texel 读自打包后的 atlas（自己那行写着 rect=2057,2057 atlas=4112x4112 size=256x256），tile 尺寸与源尺寸都是 256（1:1），而 atlas 里的内容在对应 uv 处与源 mip0 不一致，与 mip1 接近但不相等（差 6~8）。

### 3.4 alpha 消费在 HEAD 的代码现状

所以「alpha 不被消费」不是 HEAD 的代码状态：代码路径存在。该材质在运行时是否真的拿到 bit8（即是否被判成 blended、有没有被 refused 计数吃掉）本轮未证，见第 6 节 N-2。

### 3.5 D51（$basetexturetransform）对本材质的影响 = 0

实测该 VMT 里没有 $basetexturetransform（3.1 全文只有 7 个键），所以 D51 描述的缺口对这个材质的影响是 0，不是本案的机制。
两处归属纠正：

1. native/src/world_material.cpp:480 是 `SkyFaceLoad loadSkyFace(...)`（skybox 六个面的 VMT 装载），与地面材质无关，不能当作「地面材质不消费 $basetexturetransform」的位置。
2. 真正的消费者在 native/src/native_renderer_world.cpp:673-709（R2 段）：uv 先按 source 尺寸归一、(uv/sourceSize - center) * scale、旋转、再 + center + translate 回原尺度；门槛在 :691 `if (tiledMaterial.baseTextureTransform && ...)`。解析在 native/src/vmt_material.cpp:353-383（$basetexturetransform / $basetexturetransform2），日志在 native/src/main.cpp:5266-5282，传给 WorldTexture 在 native/src/main.cpp:5736-5743。
