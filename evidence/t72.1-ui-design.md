#### Focus: the one rule a new panel must inherit, not re-invent

`isTextFieldFocused()` main.cpp:2003-2010 reads `GetFocus()` and compares the focused window's CLASS NAME against EDIT, RichEdit20W, RichEdit50W. Any EDIT control a new panel creates therefore joins the focus rule for free.

`shouldDispatchHotkey` (native/src/keybinds.cpp:419-430) returns false for EVERY key while a text field is focused - the `keyIsCharacter` argument is deliberately unused (`(void)keyIsCharacter;` at 428) so a caller cannot invent a "characters go to the field, F-keys still act" variant.

The only other focus READ is native/src/logstf_panel.cpp:130 (`if (GetFocus() != g_address)`), used to avoid rewriting the address field under the cursor.

### 1.3 What can draw text and panels today

Three surfaces exist, in rising cost:

**(a) Child Win32 controls.** `createNativeUiControls` (main.cpp:1805-1922) creates them with a `make` lambda (main.cpp:1808-1813) that passes class, text, style, id, x, y, w, h to `CreateWindowExW(0, className, text, WS_CHILD | style, ...)`. All text is set by `SetWindowTextW` (call sites: main.cpp:1762, 1772, 1800, 2252, 2277, 2469). Repaints are throttled by a 14-field signature cache in `updateNativeUiControls` (main.cpp:1704-1803; tuple 1720-1726, early return 1727). Visibility is `setUiControlVisible` (main.cpp:1671-1673 = `ShowWindow(control, visible ? SW_SHOW : SW_HIDE)`). Geometry comes from `applyUiLayout` (main.cpp:533-584), called only from WM_SIZE 2329 and WM_DPICHANGED 2345.

There is one multi-line read-only text precedent in the tree: native/src/logstf_panel.cpp:215 `g_explain = make(L"STATIC", L"", SS_LEFT | SS_EDITCONTROL, 0);` with the placeholder wiring at 224-227. Every main.cpp STATIC is `SS_LEFT` only (main.cpp:1834, 1871, 1921). So a list body needs no new window class - a STATIC with `SS_LEFT | SS_EDITCONTROL` and newline-separated text is enough.

**(b) The window title.** `refreshWindowTitle` composes `fullTitle = title + playbackSuffix + demoSuffix` (main.cpp:6446-6447), calls `SetWindowTextW` 6448, and prints the same string to the trace once per change (main.cpp:6459, comment 6450-6458: under `--hidden-window` nothing reads a caption, so the trace carries it). The HUD segment comes from `composePlaybackHudLine` (native/src/native_ui.cpp:695-714), which emits exactly `tick=<n> demo=<demo> state=<state> camera=<camera> error=<error|none>`. This surface is already the tree's proven way to read a hidden window: title-capture.ps1 header 1-10, stability-run-case.ps1:155 (GetWindowTextW) and :189.

**(c) Renderer HUD primitives.** `setHudPrimitives` (native/include/native_renderer.h:1018) REPLACES the whole list, `setHudRects` (1021) converts rects to bordered Rects by calling it (native/src/native_renderer.cpp:6446-6470), `setHudEnabled` 1022-1023. Primitives have three kinds, `Rect = 0, Text = 1, Circle = 2` (native_renderer.h:1000-1046). The product has exactly three primitive call sites: the `--hud-text-test` list (main.cpp:2191), `hudApplyRects` (main.cpp:2230) and the HUD reset (main.cpp:2318). Text drawing goes through an 8x8 bitmap font that maps printable ASCII only: native/src/hud_font.cpp:165-167 `if (codepoint < 0x20 || codepoint > 0x7E) return -1;`, `hudFontGlyph` returns nullptr (177-180), and the renderer substitutes `kHudFontFallbackCell` while incrementing `hudUnmappedGlyphs_` (native_renderer.cpp:6532-6535). hud-text-check.sh:73-75 pins `EXPECT_PRIMITIVES=4 / EXPECT_TEXTQUADS=1 / EXPECT_GLYPHS=22` for that path.

**Consequence, and it decides the recommendation:** the workspace's own encoding contract says a title or note may hold any UTF-8 byte (native/include/workspace_types.h:172-178: encode everything outside [A-Za-z0-9._~-] as %XX, because a title may hold any UTF-8 byte). A HUD-primitive list can only ever show ASCII, so a Chinese bookmark title would be drawn as placeholder boxes. A child STATIC or EDIT renders Unicode natively. A list UI that cannot show the user's own note is not an honest list.

## 2. What is missing

1. No user entry point. The review code is reachable only from `--camera-script` (main.cpp:988-1002, 3416-3424), which the file itself calls TEST-ONLY, and only when `--workspace` is also given (main.cpp:4198).
2. No visible list. Nothing in the product renders a collection of rows: no LISTBOX/WC_LISTVIEW/LVCOLUMN (0 matches in native/), no HUD text list (ASCII-only, 1.3), and no GDI text in WM_PAINT (main.cpp:2561-2567).
3. No workspace controls. No menu, no button, no key for new/save/rename/autosave-status; `WorkspaceStore::rename` (review_workspace.h:103) is called from nowhere outside the script verbs, and `finish()` (main.cpp:11196) closes the workspace silently.
4. No default workspace. `setRoot` has no caller (review_workspace.cpp:881) and `pathFor` returns `{}` when the root is empty (885-890), so without `--workspace` a run has no workspace at all.
5. No UI-facing list accessor. `ReviewSession::list` is void and trace-only (review_session.h:88).
6. No failure surface. `MessageBoxW`/`TaskDialog` = 0 matches; a save refusal, a hash mismatch or an empty list can only be seen in the trace.
7. No WM_CLOSE, so "unsaved exit" has no user-facing moment at all; the only report is the shutdown trace (review_session.cpp:377-381).
8. No discovery. No `--help`, and the UI shows nothing about the workspace, so a user cannot learn that any of this exists.

## 3. Three candidate designs

### Design A - keystrokes plus the existing status line

Register `review.*` actions in a third `KeyBindTable`, handle them in a new WM_KEYDOWN block, and push one line into the existing `g_uiStatus` STATIC (main.cpp:1834, written at 1789-1800) plus one new title segment.

- New code: ~120 lines in review_panel.cpp, 4 main.cpp contact points.
- Cost: cheapest. No new controls, no new geometry, no new message cases.
- Risk: LOW on conflicts, HIGH on the review verdict. There is no list: sorting and filtering can only change a one-line summary, add/edit needs a text field, and a reviewer watching a person use it sees a status label change. This is the design a reviewer calls "still only a test channel with a shortcut".
- It also cannot show a bookmark's title, so the store's strength (titles, notes, event keys) stays invisible.

### Design B - a child-control review panel (recommended)

A new translation unit review_panel.cpp/.h that owns a panel of ordinary child controls - one multi-line STATIC for the rows, one status STATIC, two EDITs (title/note, filter) and a toolbar of BUTTONs - created, laid out, commanded and repainted exactly the way the logs panel is today (native/src/logstf_panel.cpp:195-300), plus a third keybind table for the rebindable verbs.

- New code: ~700-900 lines in review_panel.cpp (panel + its own planner + its own key table) and a ~90-line header.
- Cost: one .cpp line in native/CMakeLists.txt:146-153, and 11 named hunks in main.cpp (5.2).
- Risk: MEDIUM - the panel competes for the client rect with the logs panel (Q2), and it introduces the tree's first `SetFocus` (Q3).
- Why it is honest: every action is a control a human can click or a key a human can press; rows are the store's own records rendered as Unicode; the same functions are reachable from a keystroke, so a gate that POSTs keystrokes (evidence/t49/key-dispatch-probe.ps1:62-63) exercises the real path rather than a parallel one.

### Design C - a renderer HUD list

Draw the list as `HudPrimitive` Rect + Text primitives through `setHudPrimitives` (native_renderer.h:1018), gated so the `--hud-text-test` pins do not move (hud-text-check.sh:73-75).

- New code: ~400 lines, but it needs text layout that does not exist anywhere (no wrap, no ellipsis), plus selection highlighting and a scroll model.
- Risk: HIGH twice over. (i) The font is ASCII-only (hud_font.cpp:165-167), so titles and notes from a UTF-8 workspace draw as placeholder boxes and `hudUnmappedGlyphs_` climbs - the list would lie about user content. (ii) The primitive list is a product-wide singleton (`setHudRects` REPLACES it, native_renderer.cpp:6446-6470), so the panel and `hudApplyRects` (main.cpp:2230) would fight over it on every resize.
- It is also mouse-deaf: the renderer has no hit-test surface, so selection would have to be keyboard-only anyway.

| | A: status line | B: child-control panel | C: HUD primitives |
|---|---|---|---|
| list of bookmarks | no | yes (multi-line STATIC) | yes, ASCII only |
| sort / filter visible | summary only | yes (sort button + filter EDIT) | yes, ASCII only |
| non-ASCII titles | not shown at all | yes (Unicode control) | boxes |
| mouse affordance | no | yes (BUTTON/EDIT) | no |

| main.cpp hunks | 4 | 11 | 6 |
| collides with | nothing | logs panel rect (Q2), one SetFocus (Q3) | hud primitives + hud-text pins |
| reviewer verdict | "still a test channel" | "a real UI, cheap" | "an ASCII console on the world" |

**Recommendation: Design B.** It is the only candidate that shows the user the actual records - decoded titles and notes in the encoding the store promises (native/include/workspace_types.h:172-178) - while reusing the two mechanisms the tree has already proven with gates (child controls created by a `make` lambda and read by `SetWindowTextW`; a hidden window's keyboard driven by POSTed WM_KEYDOWN). Its cost is bounded by an existing precedent, not by new rendering technique: the logs panel is 596 lines including a browser, and this panel has no browser. A and C fail the same test in opposite directions - A cannot show the list, C cannot show the text.

## 4. The recommended design in detail

### 4.1 Geometry

A new pure planner in review_panel.cpp:


```
ReviewPanelLayoutPlan planReviewLayout(const UiLayoutPlan& base, const UiHudLayoutPlan& hud,
    int clientWidth, int clientHeight, float dpiScale);
```

- It CONSUMES `base` (native/src/native_ui.cpp:557-647) and `hud` (655-698) and writes neither, exactly as `planHudLayout` consumes `base` (native_ui.cpp:667-671 takes `lowest` as the max of `base.rects[i].y + h`). The comment there (663-666) is the rule: follow whatever is lowest, do not add a constant to a named row.
- The panel occupies a column from the HUD row's bottom + gap to `clientHeight - margin`, width `min(usableWidth, 560 scaled)`. Inside it: toolbar 30 scaled, list body = the rest minus a 28-scaled status row and two gaps, status last.
- The dpi rule must not be re-derived. `scaleDimension` is in an anonymous namespace inside native_ui.cpp (548-555) and is therefore NOT callable from another translation unit, and native/docs/camera-ui-contract.md:3 forbids re-deriving margin/gap/status geometry. So this design needs exactly one tiny shared addition: export `int uiScaleDimension(int value, float dpiScale);` from native_ui.h/native_ui.cpp (declare it and move the existing function out of the anonymous namespace - two lines, one behaviour).
- Toolbar clamp copied verbatim from native_ui.cpp:629: `rect.w = (std::clamp)(wanted, (std::min)(24, room), room)` with `room = max(0, clientWidth - margin - x)`; containment, not refusal, and `uiRectsOverlap` (native_ui.cpp:649-654) can then be asserted in a probe.

### 4.4 On-screen affordances the recommendation needs

1. **The panel itself** - a titled block (`Review workspace: <name or (unnamed)>`) carrying the 15 controls of 4.2, shown and hidden by `setUiControlVisible`-style calls. Opening it must be a visible act: rows are rebuilt from the store at open and after every mutation, never on a timer.
2. **A selection marker in text** - the `> ` prefix, because a STATIC cannot highlight. Rebuilding the body on selection change is one `SetWindowTextW`.
3. **A status line that names the last refusal** - e.g. `Jump refused: refused_out_of_range; playback stays at tick 4210`. The name comes from `reviewJumpStatusName` (review_bookmarks.h:72), the tick from `ports.tick()`.
4. **An armed-delete state** with its own text, so a destructive key is never silent.
5. **Autosave state** - the checkbox (4153) plus `autosave=on|off` in the status row; the store reports the effect as `SkippedDisabled` with reason `autosave-disabled` (review_workspace.cpp:1102).
6. **A title segment** while the panel is open, appended where `fullTitle` is composed (main.cpp:6446-6447): ` | Review: n=<count> sort=<name> sel=<id|->`. It is deliberately short because the cross-process title reader has a documented 511-character truncation history (T3-MANUAL-FOLLOWUP-2026-10-14.md:90) and the tree's reader takes the length first (stability-run-case.ps1:155, 189).
7. **A key legend inside the panel** - one STATIC line listing the verbs, because there is no `--help` and no menu anywhere to teach this.

## 6. Assertion and mutation plan (proving the UI path is real without a probe)

### 6.1 The core technique: post the keys a user would press

A gate cannot click, and a probe cannot drive the product's window. But `PostMessage(WM_KEYDOWN)` needs no focus and works on a hidden window - proved in evidence/t49/key-dispatch-probe.ps1:1-18 with the POST at :62-63, asserted by fullscreen-quiet-check.sh:682-724. T72.1 uses the same instrument on its own keys, which is legitimate because **the panel's keys are the user's keys**: there is no second code path to fake.

Per run, the gate (review-ui-check.sh):

1. Launches ONLY the product: `native/build-nmake/tf2_demo_native.exe --tf-root <tf> --demo D:/TF2_Demo_Player/testdata/demos/bb841c6d379ff7c40d0c8baf99f59d8d_matcha-20260927-1347-cp_snakewater_final1.dem --workspace <tmp.ini> --hidden-window --audio-disabled`, with `TF2_NATIVE_TRACE`. No `--camera-script` anywhere, and the gate FAILS the run if a `camera: accept` line appears - that is the proof the script channel was not used.
2. Reads the window title with a length-first buffer (stability-run-case.ps1:155, 189) and asserts the `Review: n=` segment, so the on-screen surface itself - not only the trace - is witnessed.
3. Asserts, in this order, so "empty" cannot pass as "never ran": the panel open line exists -> the `rows n=<n> sort=<name>` line -> the empty-state text when n=0 -> then the action lines.
4. Reads the workspace file's bytes: after Save the file must exist and contain `[bookmarks]`, and a second run must reopen with `bookmarks=<n>` (the roundtrip the existing gate already proves at store level, review-workspace-check.sh:198+).
5. Reads the row body from control 4141 with `GetDlgItem` + `GetWindowTextW` in the probe script. **No gate in the tree does this today** (`GetDlgItem` = 0 matches in native/src and in every *.sh/*.ps1), so the gate header must justify it: it reads the SAME control the user reads, which is the strongest witness available short of a human.

**One real constraint found while designing this, and it changes the plan:** `GetKeyState` is how every existing arm learns modifiers (main.cpp:2641-2643, 2014-2023), and a POSTed WM_KEYDOWN cannot set `GetKeyState`. A gate can therefore carry the plain tier-2 keys (Up/Down/PageUp/PageDown/Home/End/Enter/Delete/Esc) but CANNOT deliver `Ctrl+N`. Two honest options: (a) the panel's key arm takes modifiers from `lParam` (bit 29 context, and the scan-code/extended bits) rather than `GetKeyState` - a deliberate divergence from every other arm that must be documented in review-ui-contract.md; or (b) tier-1 chords are proven only by a `KeyBindTable` probe assertion plus the reported bound-chord trace line, and the gate drives the eleven BUTTONs through `WM_COMMAND` instead. **Recommend (b) for T72.1** because it changes no shared key rule, and record the limitation in the gate header rather than pretending the chord was pressed.

## 8. Open questions

**Q1 - Esc while typing.** `shouldDispatchHotkey` (native/src/keybinds.cpp:419-430) suppresses EVERY key while an EDIT has focus, and the contract makes that the shared predicate (comment main.cpp:2585-2586).
