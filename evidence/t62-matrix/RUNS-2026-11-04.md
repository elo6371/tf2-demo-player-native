## 5. The per-class pixel chain (new in this refresh)

`class-pixels-check.sh` (repository root) asks the question the single-subject
pixel gate cannot: does the drive reach the pixels of a *named body of a named
class*, for more than the one Demoman the hand-chosen camera happens to frame?

**Camera derivation.** `--debug-camera` takes `x y z pitch yaw`
(`native/src/main.cpp:2518`), and the reference eye `(5363.8, -1102.1, 5.9)`
differs from the Demoman's own origin `(5613.8, -1102.1, -52.1)` at the same
tick by exactly `(-250, 0, +58)`, with `pitch=4.1`, `yaw=0`. The script applies
that same offset to each target body's origin, so every class is viewed through
the reference geometry instead of a camera tuned per class.

**Targets are per class *and* per tick.** A recording does not keep every class
alive at every tick, and an idle body is not reported on every frame, so the
origin has to be the `anim: ent=` line of the *same* capture that gets framed.
At tick 64161 the live set is the Demoman (`ent=5`) and the Scout (`ent=15`);
the Medic is not drawn there -- a capture framed at its last reported origin
(2.5 s stale) renders props only, and `t61-entityid.py` correctly calls that
vacuous (`ENTITY-ID=FAIL`, empty body set). At tick 63000 eleven player bodies
are drawn and the Soldier `ent=2` stands clear of all of them; at tick 64000
three are drawn and the Medic `ent=13` is the only one near the view axis.
`targets.txt` therefore carries `class ent tick ox oy oz` per line.

**Framing is part of the assertion.** The first pass framed the Soldier from
`ent=2` at tick 62000 and the Medic from `ent=13` at 62000. Both frames put a
second body between the eye and the subject (Medic `ent=13` stood 118 units
ahead of the Soldier eye; Demoman `ent=4` stood 153 units ahead of the Medic
eye), so the largest body on screen was the intruder and the run correctly
refused to grade the class:

```
FAIL soldier: the largest body on screen is not this class, so the frame does not judge it:
             SUBJECT id=95 ent=13 model=models/player/medic.mdl pixels=6629
FAIL medic:   the largest body on screen is not this class, so the frame does not judge it:
             SUBJECT id=91 ent=4 model=models/player/demo.mdl pixels=4046
```

The subjects' own pixels were healthy in those frames (Soldier 1783 px / 84.52 %
motion, Medic 1692 px / 75.41 %), so only the framing was wrong; the ticks moved
rather than the thresholds. That first log is kept at
`/d/_shared/t62-class-pixels3.log`.

**Playback speed.** The chain runs at `--playback-speed 32` (about 60 s per
capture instead of 145 s at the gate's 8) and the capture still lands on the
requested tick exactly (`capture: armed requested=64161 frame_tick=64161`).
The Demoman reading is byte-for-byte the gate's: 1767 px, differ 1391,
78.72 %. The chain asserts capture determinism itself: every class captures its
`identity` frame twice, in two separate processes with identical arguments,
and the run fails unless the two BMPs are byte-identical -- the same
construction the official gate uses for its `animated`/`animated2` pair,
applied to the frame the class reading is actually taken from.

Every class is captured four times at its own tick -- `animated`, `off`
(the same capture with the drive flag simply absent; the product has no
`--player-animation-off` switch), `identity` (`--world-entity-id`) and
`identity-2` (the identical `identity` request, issued to a second process)
-- and the chain
grades the class only if the *largest player body in the frame* is that class,
so a frame that shows a neighbour better than the subject is refused instead of
being counted.

`CLASS-PIXELS=PASS` (4 of 4 named classes). Frames, per-frame summaries and the
raw `t61-entityid.py` output are committed under
`evidence/t62-matrix/class-pixels/<class>/` (`animated.bmp`, `off.bmp`,
`identity.bmp`, `identity-2.bmp`, the four `.summary` files and
`entity-id.txt`). Every `.summary` and every `entity-id.txt` ends with a
`frame:` provenance block naming the sha256 of all four frames, the sha256 of
the product executable that drew them and the exact request, so a published
count can be traced to the bytes and the binary behind it.

**The determinism assertion.** Each target's `identity` capture runs twice, in
two processes with byte-identical arguments, and the gate fails unless the two
BMPs hash the same:

    FAIL <class>: the same identity capture twice is not byte-identical, so a
    cross-run pixel count cannot be a reading (identity=<sha> identity-2=<sha>)

This is what makes every number in the table above quotable: without it the gate
publishes the pixel count of a frame it happened to get. It pins no stored
constant -- no frame hash is baked into the script -- so a relink, a different
TF install or a different machine cannot make it fail spuriously; it can only
catch the one regression that matters, the same request rendering two different
pictures. Three further assertions cover the second pass (`identity-2` exits 0,
reports view `entity-id`, and lands on the requested tick), and the frame and
product hashes are appended to each `.summary` and `entity-id.txt` as a `frame:`
block after the parsed lines.

same body with the animation drive switched off, not a speed-gated pose delta.
The Demoman cell reproduces the gate's own numbers exactly (1767 px, 1391 differ,
78.72 %), which ties the chain to the gate that the matrix already cites.

  ten hours and hashed `7317b7a2...f0e423` every time, reading 1161 px each time;

  (demo, tick, camera, flags), not a verdict that happens to agree. The single

  per-target driver generation, which mis-framed Soldier and Medic in that same
  run (see `targets.txt`); no frame on disk carries that count. What does move
  between processes is the wall-clock number of frames drawn before the capture
  and every counter derived from it (`boneMismatch`, `cycle`, `poseChanges`,
  `advances`), because the replay advances by wall-clock time
  (`native/src/main.cpp:454`, `kTargetFrameSeconds = 1/120`): pin the frame hash
  and the mask count, never the cumulative counters.

### 15. The hole criterion was measuring the instrument, not the frame

Until this pass the geometry axis on the map matrix rested on one rule: *where the
map's own sky brushes cover at least 90 % of the pixels no world triangle drew,
the pixels they do not cover are at most 5 % of that population.* The reading
behind the rule is the share of empty pixels that the BSP sky-brush mask covers,
and that share is a property of the map's construction, not of the renderer:

| map | empty pixels the BSP sky-brush mask covers | what the old rule did with them |
|---|---|---|
| pl_odyssey | 100 % | judged |
| cp_snakewater_final1 | 98.2 % | judged, 3,824 px "unexplained" |
| koth_bagel_rc11 | 62.9 % | `SKY-INSTRUMENT=unavailable` -- the masks cannot name this map's sky |
| koth_bagel_rc12 | 11.3 % | `SKY-INSTRUMENT=unavailable` |
| cp_sunshine | 0.4 % | `SKY-INSTRUMENT=unavailable` |

So on three of the five maps the geometry axis was not judged at all, and on the
fourth the number it published was an artifact. The product draws its sky as a
six-face cubemap (`gpu: world sky-upload state=active vertices=36 triangles=12
faces=6 side=512`, and one `world sky-face` line per shelf: `rt`, `lf`, `bk`,
`ft`, `up`, `dn`); the BSP sky brushes are a small box around the map, and an
open sky pose simply looks past it.

**What the 3,824 pixels were.** `--world-hole-trace` runs the renderer's own
projection over every world triangle and reports, per screen point, whether a
triangle covers it under the cull/PVS state (`drawn`), with both restrictors
off (`any`), and whether a BSP sky face covers it (`sky`). On nine points taken
from the "unexplained" population of `cp_snakewater_final1` (tick 2000, same
camera), eight printed `drawn=- any=- sky=- frameDepth=1.0000` -- there is no
world triangle *and* no BSP sky face anywhere along the ray -- and the ninth hit a
sky face (`sky=face=5251 material=TOOLS/TOOLSSKYBOX tri=274`). Eight of the nine
pixels the old rule called unexplained were open sky.

**The criterion that replaces it.** `--world-flat --no-world-sky` removes both the
texture pass and the cubemap, and the frame then contains exactly two colours:
the flat world colour `(89,158,97)` (`native/src/native_renderer_shaders.cpp:166`)
and the clear colour `(14,18,22)`. "No world triangle drew this pixel" becomes
computable per pixel instead of inferred from a mask. Four captures per map make
the population an algebra rather than a threshold:

| capture | flags | what it isolates |
|---|---|---|
| `flat-base` | `--world-flat --no-world-sky` | what the renderer draws with its own restrictors on |
| `flat-novis` | `+ --no-world-vis-clip` | what the PVS clip removes |
| `flat-nocull` | `+ --no-world-cull` | what backface culling removes |
| `flat-novis-nocull` | both | every pixel some world triangle covers |

and the assertions are set relations, not counts:

- **G4** the empty population is not empty (otherwise G5-G7 are vacuous).
- **G5** nested: `base ⊆ vis-off`, `base ⊆ cull-off`, and both of those `⊆` both-off. A pixel the renderer drew with a restrictor on must still be drawn with it off; a pixel it drew with both off must be drawn with each one off.
- **G6** attribution: the pixels the two restrictors remove are accounted for as `cull-only + pvs-only - overlap`, and that union is at most what removing both removes together.
- **G7** lighting is one-way: a pixel whose *albedo* is dark must also be dark in the lit frame; the converse is not required (a shadow is legitimately dark over bright albedo). The lit frame is `lmoff` (albedo only), so the comparison is albedo against albedo+lightmap.
- **G8** the oracle explains the two kinds of empty pixel: an `open` sample (empty in both base and both-off) must have `drawn=-` *and* `any=-`; a `removed` sample (empty with restrictors on, drawn with them off) must have `drawn=-` and `any=face=`.

`LATTICE_SAMPLES=6` is fixed-ratio deterministic sampling and works only because the
lattice generator itself is deterministic from bytes (*x* and *y* are *offset/stride*,
*z* is a function of the aligned index). That is why only six samples are needed for
a wide random read.

| cp_snakewater_final1 | 618,381 | 242,403 | 214,560 | 4,523 | 5,340 | 62 | 9,801 | 27,843 | ok |

**The coupling the oracle costs.** The eleventh capture per map passes

### 16. `boneMismatch` is a property of the assets, so the gate pins what it counts

The trace line `scene: anim ... boneMismatch=N` reads like a health metric, and the
tempting gate is "it must be zero". On this tree that gate would be wrong. The counter
increments once per skinned instance per update when the instance reports a skin-matrix
count that disagrees with its declared bone counts (`native/src/main.cpp:9179-9182`:
`sampled.skinBones != sampled.validBones || sampled.skinBones != sampled.skinMatrices.size()`),
it is never reset (`resetPerUpdate()` at `native/src/main.cpp:3346-3372` does not touch it,
so it accumulates over every update of the run), and the honest cause on this corpus is a
**helper bone**: a bone with a valid bind transform and no animation channel. Demoman,
Heavy and Scout have two such bones each and the other six classes have none, so the
counter separates "this model has helper bones" from "it does not" -- an asset property,
not a fidelity measurement.

`validBindBones - renderBones` (`native/src/animation_binding.cpp:508-529`), and it is
exactly 2 on demo (84/82), heavy (79/77) and scout (78/76), 0 on the other six. Observationally,
on the 1,192 scene updates of a driven run the increment per update equals the number of
those three models drawn in that update on all 256 updates whose census is complete
(`census-fit=256/256`), and the residual is positive only on the truncated updates
(`residual={1: 365, 2: 570}`).

### 19. The hole criterion, rebuilt: five maps pass on set algebra instead of a sky mask

§15 recorded why the old empty-pixel rule had to go: it decided "hole" by asking whether a
BSP sky brush sat behind the pixel, but the product draws sky from a six-face cubemap, so the
mask measured how each map was built, not whether the renderer left a gap. The gate now runs
four captures of the same pose with `--world-flat` and two restrictors, and reasons about sets
instead of a mask.

**The four captures** (all `--world-flat`, same tick 2000, same camera, asserted identical
`scene: camera` eye): base (both restrictors on), `--no-world-vis-clip`, `--no-world-cull`,
and both off. In a flat frame the world pass paints one colour and nothing else does, so a
pixel is *drawn* exactly when it equals the flat colour -- the cubemap never enters these
frames, which is why `clear` counts zero in all twenty of them and why an earlier draft that
tested "not clear" degenerated to "everything is drawn".

**What the gate asserts now** (`map-geometry-lighting-check.sh`):

| # | assertion | why it cannot pass vacuously |
|---|---|---|
| G4 | the both-off capture has both painted and unpainted pixels | an all-painted or all-empty frame makes every later set comparison trivial |
| G5 | base drawn subset of novis drawn subset of both-off drawn (and base subset of nocull) | each restrictor may only *add* pixels; a removable pixel that stays painted under a relaxed restrictor is a contradiction |
| G6 | cull-only union pvs-only, minus their overlap, equals the pixels the two restrictors share; the union is no larger than the both-off gain | attributes every recovered pixel to culling, PVS or both |
| G7 | every albedo-dark pixel is frame-dark, and the dark population is not empty | the lighting account cannot be satisfied by an empty set |
| G8 | on sampled empty pixels the point oracle finds no contradiction | `--world-hole-trace` re-projects the display triangles and reports what the ray hits |
| L2 | the dark-account buckets partition the dark population, with no ambiguous bucket | a true partition: the buckets sum to the total by construction |
| L3 | product-attributable dark pixels <= 2 % of the frame | a decoding regression would darken a whole lightmap rectangle, an order of magnitude above the ceiling |

**The oracle** is what makes G8 a measurement rather than a threshold. `--world-hole-trace`
takes screen points, walks the display triangles and the BSP sky triangles for that exact
pose, and prints what the ray meets (`drawn=` respects cull and PVS, `any=` ignores both).
A point the gate calls *open* must have neither a drawn nor any triangle on the ray; a point
it calls *removed* must have no drawn triangle but at least one culled triangle or sky face.
The gate samples empty pixels from the both-off capture, and burns the oracle into a capture
that is asserted byte-identical to the flat base frame, so asking the question cannot change
the picture being judged.

### 20.1 The one red: a gate-side bug, not a product regression

The appearance step is the only step that did not finish green. Its own body-level
assertions all passed -- `red-demo` mask 1538 px with `r-b 48.1`, `blu-demo` 1588 px with
`b-r 21.6`, `red-scout` 1129 px with `r-b 89.3`, `blu-scout` 847 px with `b-r 43.8` -- and
those four readings are identical to the ones recorded in section 18. What failed is the
bookkeeping that decides whether a two-team batch may claim a pair:

```
player-body-appearance-check.sh: line 217: rb rb: invalid variable name
  OK   this batch requests one team per class, so it makes no pair claim (...)
player-body-appearance-check.sh: line 235: 2,3, 2,3,: invalid variable name
  FAIL a two-team batch judged bodies in team(s) <none> only; a team claim needs at least one body per team
```

The cause is the key-iteration idiom written for the pair rework: for CLASS in ${!WANT_TEAMS[@]+"${!WANT_TEAMS[@]}"}.
On an **associative** array bash re-reads that form as an indirect expansion, prints
`invalid variable name`, and abandons the loop body, so every pair counter stays zero and
the final consistency check sees an empty judged-team set. Reproduced in isolation on the
same shell (GNU bash 5.3.15(2)-release): the same snippet with a plain "${!ARR[@]}" is clean,
including on an empty array under `set -u`. Section 18's single-team batch never hit it
because that path makes no pair claim, which is exactly why the two-team batch had to be
run again to expose it.

**Disposition.** The original failure was kept, not overwritten: `appearance.log` above is
the failing run. The fix is a two-line change (plain key expansion in both places, plus a
comment recording the trap), and the corrected run is the `appearance-fixed.log` row in the
table: `BODY-APPEARANCE=PASS`, rc=0, `PAIR demo red-minus-blu gap = 69.7` and
`PAIR scout red-minus-blu gap = 133.1`, both above `PAIR_MIN_GAP=40`.

**What was deliberately not done**: the other twelve steps were not re-run after the fix.
They ran on the same tree and the same binary as the corrected appearance run, their logs
are untouched, and the failing step's output path is separate
(`T62_BODY_OUT=/d/_shared/t62-freeze3/appearance`). Re-running the whole sweep would
re-measure eleven gates that were never in question; if a later change ever touches the

## 22. 水面表面：法线图当颜色 → 一张真正的水贴图（2026-11-05）

**P1-2a, a cull control.** `cull-control.py` reads the `ids` and `ids-nocull`
frames (the face id the product itself wrote per pixel) with the BSP, and asks which
faces the cull removed, on which side of their plane, and how many pixels each
removal accounts for. A control that removes nothing measures nothing, so each pose
fails when its cull removes nothing; a negative control copies `ids.bmp` over
`ids-nocull.bmp` and requires `CONTROL=FAIL the cull removed nothing`, so the
control is known to be able to say no. In the delivered pass all ten poses printed
`OK the cull control rejects a cull that removes nothing (negative control)`.

Two numbers from that control are **readings, never assertions**:

- `onlyInCull` is a bound, not zero. Coincident faces and shared edges land on
  different face ids in the two frames, so a few face-id pixels appear only in
  the culled frame: cp_sunshine pose 1 measured 4 of its 394,774 kept pixels
  (10 ppm), cp_snakewater_final1 pose 1 2 of 617,852 (3 ppm), pl_odyssey pose 2
  2 of 753,698 (2 ppm), and the other seven poses 0. The gate refuses more than
  0.1% of kept (1000 ppm) as a loose sanity bound; it does not claim the two
  frames are a subset beyond that bound.
- the cull control's `removed` is not the lattice's `union`, and
  `drawn_alloff - union == drawn_base` is **false**. Measured on cp_sunshine
  pose 1: `drawn_base=444373`, `drawn_alloff=472566`
  (`evidence/t62-map-axes/cp_sunshine/lattice.txt`), `cull_only=2640`,
  `pvs_only=17614`, `union=20254` and the control's `removed=10621` (delivered
  log). 472566-20254=452312 is 7939 pixels short of `drawn_base`, because the
  faces behind a removed face are drawn once the face in front of them is gone,
  while the control counts only the pixels that carried a removed face's id.
  The gate prints the two accounts side by side (the `reading: lattice` line even
  carries `vs control removed=`) and asserts neither against the other.

**P1-2b, the pictures are pinned.** Every map and pose writes
`evidence/t62-map-matrix/<map>/frame-pins-<pose>.txt`: head, time, reason, the
product sha256, the pose, and the sha256 of each of the ten world frames the pose
captures (the oracle differential frame is captured later in G8 and is not pinned).
A pin that stops matching prints `THE PICTURE MOVED` and fails: that says the
product draws something else now, not that the gate broke. `--re-pin=<why>`
rewrites the reference, keeps the previous header and records the reason, and the
run refuses to write a first reference without a reason.
`cull-reference-<pose>.txt` pins the cull account the same way.

Captures also have one picture size per pose now. One capture came back 833x439
against the run's 1264x681 on 2026-11-05 (the first capture of a process, not
reproducible in three fresh single runs). `capture()` retries a size mismatch once
and logs it; if the size is stable it adopts it and recaptures the frames that
disagree, and a frame that still disagrees fails. The hole account compares frames
pixel for pixel, so one size per pose is a precondition, not a tolerance. The ten
pose size records (`.size` in `.scratch/t62-map-axes/<map>[/p2]/`) all read
1264x681, so every frame the delivered pass used is that size.

**Coverage is counted per map, not per pose.** Three readings prove a pose was not
vacuous: it leaves at least one empty pixel (G4), at least one dark-albedo pixel
(G7), and its cull removes at least one face-id pixel (P1-2a). Requiring each of
those at every pose would make the verdict depend on one map's sky distribution
rather than on the product: pl_odyssey pose 1 is the only one of the ten screened
cameras on that recording that leaves any pixel empty, so the turned second camera
there has `empty=0` and still draws (its base capture has
`flat-base colours flat=754512 clear=0 other=106272`). The three are therefore
summed across the poses of a map and asserted per map (the per-map table below
shows which pose pays), and a pose that sees no depth at all is a different thing
and still fails by name: when every pixel of its flat frame is one colour the gate
says the camera sits inside the world (that is how the pl_odyssey tick-12000 camera
was caught) -- a pose with depth and no empty pixel is not that.

### What this does not claim

### 25.3 The animation-drive gate: two red readings, one gate bug, one false premise
