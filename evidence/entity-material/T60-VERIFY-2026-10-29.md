## 2. Static review of the product diff (before any build)

Read in full: `git diff HEAD -- native/`, `git diff HEAD -- mutate.sh`.

* `accepted` is incremented once per entity that reached a bucket
  (`native_renderer.cpp:4152`), and the numerator is
  `entityModelTexturedInstanceCount_ += range.instanceCount` guarded by
  `instanceCountedAsTextured`, once per bucket (`:4189-4196`). `range.instanceCount`
  is `bucket.items.size()`, i.e. the same unit as `accepted`. Denominator and
  numerator are therefore the same unit; `N/N` is reachable, and a bucket with no
  textured run lowers both sides' agreement rather than inflating one.
* `entityModelInstanceSlotCount_` is reset at all four sites (upload mesh, set
  instances, and two failure clears) and written once, from `packed.size()`. It is
  published, never used as a denominator.
* Paint and draw both derive the family from the same helper
  (`selectableSkinFamilyCount` for the upload loop, `effectiveSkinFamily` for the
  draw). The draw's `drawnSkinFamilyCount` comes from `entitySkinFamilyCountByKey`,
  filled at preparation from `prepared.skinFamilies.families.size()` — the same
  table the upload loops over, so key and lookup cannot disagree.
* `resolveMaterialSlot` is unchanged, so the probe can still report "family 1 is
  absent"; only the caller's choice of family changed. No threshold was relaxed and
  no assertion in `entity-material-check.sh` was edited (the file is byte-identical
  to HEAD).
* m12's new anchor is the call that exists at `main.cpp:7427`; patching it to
  `if (false && renderer.uploadEntityModelTexture(prepared.cacheKey,
  painted.materialSlot, painted.skinFamily,` keeps the arguments (and the
  resolution above them) in the binary, so the mutation removes the upload and not
  the resolution.

## 6. The two reds in §5, and why they block the freeze

They are **not** caused by the staged T60 fix and **not** caused by input drift.
They are caused by the animation-source change in `0819fce` (the already-committed
T60 commit, subject line "…and pick the real animation source"), which is what the
tree has been carrying since 2026-10-24 and which no gate has measured since.

**Step 22** — `models/player/scout.mdl --model-sequence 0 --model-tick 30`:

```
committed 2026-10-21 (evidence/weapon-animation/readings.txt:11)
  model-animated: gpu: model skin source=animated bones=78 uploaded=78 skinning=1 seq=0 frame=0/1 reason=ref
this run
  animated:       gpu: model skin source=identity bones=78 uploaded=78 skinning=1 seq=0 frame=0/0 reason=sequence has no animation binding
```

The supplied sequence no longer binds, so the pose is the bind pose; the two
assertions that depend on it follow — `a supplied sequence produces an animated
pose = identity, expected animated` and `the silhouette rule did not reject a real
pose change (rc=0)`, plus `a sampled sequence moves the geometry (rc=1)`.

**Step 23** — four readings moved, all of them frame counts or a sequence index
that the animation table decides:

```
pov refusal sequence                 28   (expected 29)
pov companion frame count            31   (expected 51)
pov history frame count               1   (expected 61)
matcha pairing scene line    no longer contains "ViewModel entity names the view entity in m_hOwner"
```

Attribution, and what rules the alternatives out:

* `native/src/animation_binding.cpp`'s last change is `0819fce`, and its diff
  replaces the first-match companion rule with "score every declared
  `_animations.mdl` companion by how many of the model's own sequences it binds and
  keep the best". Changing which table is adopted changes exactly the quantities
  that moved: binding by index (`seq 0`), and per-clip frame counts (51→31, 61→1).
* The demo, the VPKs and the model inputs are unchanged: the demo is
  `308cc145…` (Sep 30), and `tf2_misc_*.vpk` mtimes are 2026-07-08…2026-10-06, all
  older than the 2026-10-21 reading. So the input did not move; the tree did.
* The staged fix in §1 touches none of this: its diff is the paint-family helpers,
  the instance/slot split, and the title fields.

Why this blocks P4 rather than being a footnote: `verify-all.sh` marks step 22/23
as FAIL on any assertion mismatch (57 and 154 OK are pinned), so a frozen chain run
on this tree cannot reach 30/30. Fixing it is a decision about product semantics —
either `--model-sequence` is resolved against the model's own table (restoring the
2026-10-21 reading), or the two gates' hard-coded 29/51/61 are updated because the
adopted table legitimately changed. The second option rewrites the numbers the
acceptance rests on and must not be done quietly; the first changes which table the
product poses a standalone `--model` from. Neither is in T60's paint scope, and
either needs its own positive gate plus a mutant. **No fix was attempted.**

## 7. What this does not prove

* The full chain was not run. Steps 1–7, 9–15, 17–19, 24–30 have no reading from
  this round, and §6 shows the tree would fail at 22 and 23 if it were run now.
* `entityModels=95` / `entitySlots=201` are printed, not asserted
  (`entity-material-check.sh:280`); `N/N with N > 0` would also accept a fix that
  drew fewer instances. The number is published so a later round can pin it.
* The skin-family clamp has no mutant of its own; m12 removes the upload, not the
  clamp. A mutant that kept the phantom family-1 request would redden the same
  three readings (that is what the pre-fix tree did), so the clamp is proved by the
  pre-fix record, not by a named case in the suite.
* **The exe sha256 is not stable across rebuilds of identical sources.**
  `eacef9b5…` → `91e04087…` → `d6bb72e2…` were produced from byte-identical sources
  (the four sha256 in §1 never changed); the PE header carries a link timestamp. So
  recording "product exe sha256" as the chain's identity cannot prove a later binary
  was built from the same commit — the source sha256 can. Anyone freezing the tree
  should record both and treat only the source hash as a claim about provenance.
* No human looked at a frame. The paint verdict rests on the gate's pixel layer
  (30 changed pixels in the model block) and on the counters.
* **Open observation, not a verdict: the 22 gate's three demo captures are one
  picture.** `tick-2000.bmp`, `tick-4000.bmp` and `tick-6000.bmp` in
  `.scratch/t60-verify/22/` are byte-identical to each other *and* to the
  entity-material gate's tick-3000 frame (`96b412c7…`); the gate asserts that as
  "the camera reading resolved a branch = still" and "frames of a still camera are
  one picture", so its own assertions pass. A two-launch control settles that
  `--capture-tick` itself is honoured: the same binary, same demo, ticks 1000 and
  3000 produce `1163bf27…` and `96b412c7…` with traces reading
  `capture: armed requested=1000 frame_tick=1000 frames=978` and
  `requested=3000 frame_tick=3000 frames=2966`. So the coincidence lives in the
  22 gate's invocation (it is the one that adds `--metrics-file`), not in the
  entity-material capture. Not diagnosed further, not fixed, and it does not
  affect any reading in §3–§5: the entity-material frame is the tick-3000 frame,
  and the weapon gate's section 1 passes on its own terms.
