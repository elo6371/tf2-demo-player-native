# The recordings viewmodel-animation-check.sh reads, pinned by size and sha256.
#
# WHY A PINNED FILE AND NOT A GLOB
#   The Steam demos directory is LIVE -- 3623 entries on 2026-10-11, and
#   recordings land in it while a round is being worked on. A gate that globbed it
#   would compare a different set on every machine and on every day, and step 9 of
#   the acceptance chain already went red for exactly that reason (2026-10-08, a
#   sample drawn from the live directory moved to neighbouring files and 23 of 24
#   frozen reports stopped being read). The same rule applies here.
#
# TWO RECORDINGS, BECAUSE THEY ANSWER TWO DIFFERENT QUESTIONS
#   pov    -- svc_SetView names a player who owns a ViewModel entity, so the
#             entity's m_nSequence is READ and the refusal is reachable. Measured:
#             viewEntity=18, two CTFViewModel entities owned by it, sequences 0..34
#             against a drawn table of 7.
#   matcha -- the view entity owns NO ViewModel entity (measured: viewEntity=1,
#             entitiesOwnedByViewEntity=0), so the pairing fails and the product
#             reports `missing`. A gate that only ever saw the first recording
#             would not know the second state exists, and "the pairing works" is
#             not true in general -- it is true of one recording.
#
# A MISSING OR CHANGED FILE IS A FAIL, NOT A SKIP
#   "the input is not here" and "the input is clean" must not read the same. The
#   gate prints which of the three it was (absent, wrong size, wrong hash).
#
